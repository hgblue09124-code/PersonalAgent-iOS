# M5 — Local + Cloud Storage / Sync Architectural Specification

Status: ARCHITECTURE DEFINITION — READY (NO PRODUCTION CODE IMPLEMENTED)

Milestone 5 (M5) extends M4 Memory persistence and general agent state storage with synchronization capabilities across local and cloud persistence boundaries, maintaining strict local-first operation without coupling the Kernel or Memory subsystems directly to any cloud vendor.

---

## 1. High-Level Architecture & Layer Boundaries

M5 establishes a clear separation between local persistence, cloud adapters, and the synchronization engine.

```
                    ┌──────────────────────┐
                    │       Kernel         │
                    └──────────┬───────────┘
                               │ explicit port
                               ▼
                    ┌──────────────────────┐
                    │   Storage Contract   │
                    └──────────┬───────────┘
                               │
             ┌─────────────────┴─────────────────┐
             ▼                                   ▼
    ┌──────────────────┐                ┌──────────────────┐
    │ Local Persistence│                │ Cloud Persistence│
    └──────────────────┘                └──────────────────┘
             │                                   │
             └─────────────────┬─────────────────┘
                               ▼
                    ┌──────────────────────┐
                    │     Sync Engine      │
                    └──────────┬───────────┘
                               ▼
                    ┌──────────────────────┐
                    │ Consistency/Recovery │
                    └──────────┬───────────┘
```

### Important Architectural Distinction

M5 MUST NOT be designed as a direct pipeline from Memory to Cloud (`Memory → Cloud`).
Instead, M5 is designed as:

```
Memory
   ↓
Storage Contract
   ↓
Local Persistence
   ↕
Sync Engine
   ↕
Cloud Persistence
```

- **Memory** persists locally using local storage implementations conforming to `StorageContract` (e.g., `FileBackedMemoryStore`).
- **Local Persistence** remains authoritative for offline agent execution.
- **Sync Engine** owns synchronization semantics, conflict detection, resolution, and state convergence between Local and Cloud persistence.
- **Cloud Persistence** acts purely as a durable remote state store behind a vendor-agnostic adapter boundary.

## 2. Structural Sub-Milestone Boundaries (M5.1 — M5.5)

### M5.1 — Storage Contract & Boundary
- **Focus**: Core storage abstraction, ownership model, identity typing, versioning semantics, and explicit dependency direction.
- **Key Concepts**:
  - `StorageRecord`: Unified contract with stable `id: String`, `updatedAt: Date`, and `version: Int`.
  - `LocalStore`: Interface for fast, atomic local CRUD operations.
  - Ownership: Explicit local store actors owned by Composition roots (`M5CompositionRoot`).
  - Strict dependency rules enforcing zero import of cloud vendors or concrete storage engines into Kernel/Memory.

### M5.2 — Cloud Persistence
- **Focus**: Concrete cloud persistence adapter interfaces, durable upload/download operations, and provider-independent contracts.
- **Key Concepts**:
  - `CloudStore`: Generic contract for remote record push/pull.
  - `CloudStorageProvider`: Abstract provider adapter interface defining identity and availability (`isAvailable: Bool`).
  - Complete isolation: Cloud vendor SDKs (e.g. CloudKit, REST/S3 wrappers) live inside private adapter implementations; no vendor leaks into `PAKernel`, `PAMemory`, or `PAStorage` contracts.

### M5.3 — Sync Engine
- **Focus**: Bidirectional synchronization between local and cloud persistence, deterministic ordering, conflict detection, and resolution.
- **Key Concepts**:
  - `SyncEngine`: Runtime actor that processes local change queues and pulls remote change sets.
  - Conflict Detection: Comparing local and remote version numbers (`version`) and modification timestamps (`updatedAt`).
  - `SyncConflict`: Encapsulates diverging `local` and `remote` versions of a `StorageRecord`.
  - `ConflictResolution`: Explicit policy enum (`keepLocal`, `keepRemote`, `merge`, `requireUser`). Overwrite without conflict strategy is strictly forbidden (`StorageBoundary.forbidsOverwriteWithoutConflictPolicy = true`).
  - Idempotency & Retry: All sync actions are idempotent keyed by record `id` and revision hash.

### M5.4 — Recovery & Consistency
- **Focus**: Fault tolerance, handling interrupted network/disk operations, partial sync recovery, and offline → online state transition guarantees.
- **Key Concepts**:
  - Local Sync Log / Change Queue: Local mutations are recorded in a durable changelog before sync attempt.
  - Retry semantics: Exponential backoff with jitter for network transients; zero corruption of local state if network fails mid-sync.
  - Transaction safety: Partial sync failures leave local storage in a consistent state and flag pending records for future sync retry.

### M5.5 — Performance & Integration Gate
- **Focus**: Large dataset stress testing, concurrent local/cloud execution, failure injection, deterministic state convergence verification, and final integrity audit.
- **Key Concepts**:
  - Verification with thousands of records under simulated high latency and dropped network connections.
  - Failure injection: Simulating process crashes, partial packet loss, and concurrent local updates during sync.
  - Final architectural integrity audit ensuring zero regressions to M0–M4.

## 3. Explicit Architectural Invariants

M5 enforces 14 mandatory architectural invariants:

1. **Local-first**: Local state remains fully operational without active network connectivity or cloud availability.
2. **Cloud is not Kernel**: Kernel must never import or depend directly on any cloud SDK, vendor, or network layer.
3. **No service locator**: All dependencies are injected explicitly via Composition wiring (`M5CompositionRoot`).
4. **No singleton/global storage**: Storage ownership is explicit and actor-isolated; global static storage singletons are strictly forbidden.
5. **Memory remains independent**: `PAMemory` contracts (`MemoryExecuting`, `MemoryStore`) must remain cloud-agnostic and retain their local-first snapshot guarantees.
6. **Sync is a separate capability**: Storage persistence (reading/writing records) and state synchronization (replicating state across nodes) are separate responsibilities.
7. **Conflict semantics must be explicit**: Systems must never silently overwrite divergent local or remote state. Conflicts must be explicitly detected and resolved via `ConflictResolution` policies.
8. **Idempotency**: Retrying any push, pull, or sync operation must produce identical logical state without producing duplicate records or orphaned entities.
9. **Determinism**: Given identical initial local and cloud states alongside the same event history and conflict resolution policy, sync resolution must yield identical results across all nodes.
10. **Failure must be observable**: No `try?` or silent swallowing of errors on critical persistence, IO, or synchronization paths. All errors are typed and surfaced.
11. **Offline operation**: Cloud network unavailability or remote server errors must never corrupt valid local state or block local agent operations.
12. **Versioned state**: Records and sync operations must carry explicit version numbers (`version: Int`) and timestamps for revision checking.
13. **Vendor isolation**: All cloud-specific vendor code lives behind abstract adapter boundaries (`CloudStore`, `CloudStorageProvider`).
14. **No M6 leakage**: M5 must not introduce authentication, user login, token refresh, or secret management into storage contracts, unless required to define pure protocol boundaries (credentials resolved via `PASecurity`).

## 4. Architectural Design Q&A

### Q1: Who owns local state?
**Answer**: Local state is owned by the local persistence layer (`LocalStore` implementation, e.g., `FileBackedMemoryStore` or local database actor). The application process owns this actor. Local state is the authoritative source of truth for all local agent processing.

### Q2: Who owns cloud state?
**Answer**: Cloud state is owned by the remote cloud persistence layer, managed behind the abstract `CloudStore` protocol. It represents the synchronized remote snapshot or event stream.

### Q3: Who is allowed to mutate each?
**Answer**:
- **Local state**: Mutated by local subsystems (e.g. `PAMemory`, `Kernel` via ports) during normal operation, and by `SyncEngine` when applying remote updates or resolved conflicts down to local storage.
- **Cloud state**: ONLY the `SyncEngine` is permitted to write/mutate cloud state via `CloudStore.push()`. Neither `Kernel`, `PAMemory`, `PAUI`, nor any module/skill/tool may call `CloudStore` directly.

### Q4: What is the identity of a stored object?
**Answer**: A stable string key (`id: String`). For memory records, this is `MemoryRecordID.rawValue`. Identity is immutable across local and cloud copies.

### Q5: How is version/revision represented?
**Answer**: Version is represented by an explicit integer `version: Int` on `StorageRecord` (incremented on every record mutation), combined with `updatedAt: Date` (ISO-8601 timestamp) and optional revision content hashes.

### Q6: What happens when local and cloud diverge?
**Answer**: Divergence is detected when local record `version` / timestamp differs from remote record `version` / timestamp for the same `id`. The `SyncEngine` creates a `SyncConflict(local: remote:)` and applies an explicit `ConflictResolution` policy (`keepLocal`, `keepRemote`, `merge`, or `requireUser`). Silently overwriting without conflict resolution is strictly forbidden.

### Q7: What happens offline?
**Answer**: The agent operates completely normally using `LocalStore`. Local modifications update the local state immediately and append record IDs to a local durable sync change queue (`enqueueLocalChange(id)`). Cloud operations are deferred until network connectivity is restored.

### Q8: What happens after retry?
**Answer**: Sync operations are designed to be idempotent. Retrying a push, pull, or conflict resolution for a record `id` idempotently reconciles the record using version checks, resulting in the exact same merged state without duplicate records or revision counter inflation.

### Q9: What happens after partial failure?
**Answer**: Operations execute within transactional snapshot boundaries. If a cloud push fails mid-batch, successful items update their sync status while failed items remain in the local pending change queue. Local disk storage retains atomic snapshot guarantees (`Data.write(..., .atomic)`), ensuring disk integrity is never compromised.

### Q10: What guarantees are deterministic?
**Answer**:
1. Conflict resolution given identical local record, remote record, and policy returns identical resolved record.
2. Inverted index and version ordering on local store reload match across all process runs.
3. Sync change queue processing order is strictly sequential by modification sequence.

### Q11: Which layer knows about the cloud?
**Answer**: Only concrete cloud adapter implementations (e.g. `PAStorageCloud` or vendor-specific swift files) and the `SyncEngine` runtime know about cloud transport protocols.

### Q12: Which layer must NEVER know about the cloud?
**Answer**: `PAKernel`, `PAMemory`, `PACognition`, `PAAgency`, `PAPolicy`, `PASkills`, `PATools`, `PAModules`, and `PAUI` must NEVER know about or import cloud providers, cloud SDKs, or cloud storage abstractions.

### Q13: How will M5.1 → M5.5 be implemented incrementally?
**Answer**:
- **M5.1**: Define storage protocol contracts, record types, and local store interfaces.
- **M5.2**: Implement cloud store adapter interfaces and mock cloud persistence fixtures.
- **M5.3**: Build `SyncEngine` runtime actor, conflict detection, and policy resolution algorithms.
- **M5.4**: Implement persistent change log queue, retry policies, offline transition hooks, and failure recovery.
- **M5.5**: Add integration test suites, large-scale dataset benchmarks, fault-injection tests, and verify overall integrity.

## 5. Dependency Direction & Graph

The architectural dependency flow for M5 strictly follows the hierarchy below:

```
                  ┌───────────────────────┐
                  │    PAComposition      │
                  └──────────┬────────────┘
                             │
       ┌─────────────────────┼─────────────────────┐
       │                     │                     │
       ▼                     ▼                     ▼
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│   PAKernel   │      │   PAMemory   │      │  PAStorage   │
└──────────────┘      └──────────────┘      └──────┬───────┘
                                                   │
                                     ┌─────────────┴─────────────┐
                                     ▼                           ▼
                            ┌─────────────────┐         ┌──────────────────┐
                            │ Local Storage   │         │ Sync Engine      │
                            │ (LocalStore)    │         │ (SyncEngine)     │
                            └─────────────────┘         └────────┬─────────┘
                                                                 │
                                                                 ▼
                                                        ┌──────────────────┐
                                                        │ Cloud Persistence│
                                                        │ (CloudStore)     │
                                                        └──────────────────┘
```

### Import Rules
- `PAKernel` imports `PAFoundation`, `PAEvents`, `PAObservability`. Kernel DOES NOT import `PAStorage` or cloud packages directly (communicates via generic coordination ports if needed).
- `PAMemory` imports `PAFoundation`, `PAEvents`, `PAObservability`. `PAMemory` conforms to storage contracts where appropriate but DOES NOT import cloud persistence or sync engines.
- `PAStorage` defines core storage contracts (`StorageRecord`, `LocalStore`, `CloudStore`, `SyncEngine`, `ConflictResolution`).
- Concrete Cloud Adapters import `PAStorage` and `PAFoundation`. They do not import `PAKernel` or `PAMemory`.
- `PAComposition` wires `LocalStore`, `CloudStore`, and `SyncEngine` together.
