# M5 — Local + Cloud Storage / Sync Architectural Specification Contract

Status: ARCHITECTURAL CONTRACT SPECIFICATION — FROZEN (NO PRODUCTION CODE IMPLEMENTED)

This document defines the normative architectural contract for Milestone 5 (M5: Local + Cloud Storage / Sync). It establishes strict structural boundaries, state ownership rules, revision tracking semantics, and synchronization invariants.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

---

## 1. Architectural Scope & Non-Goals

### 1.1 Architectural Purpose
M5 extends local agent state persistence with vendor-agnostic cloud synchronization capabilities while preserving absolute local-first operation.

### 1.2 Non-Goals & Implementation Independence
To guarantee architectural longevity and prevent premature coupling, M5 contracts MUST NOT dictate:
* Concrete database technologies (e.g. SQLite, CoreData, Realm, key-value engines).
* Specific cloud vendor SDKs or hosting providers (e.g. CloudKit, Firebase, Supabase, AWS S3).
* Network transport protocols, frame formats, or RPC frameworks.
* Concrete retry algorithms, backoff schedules, or jitter parameters.
* Specific serialization formats (e.g. JSON, Protocol Buffers, MessagePack).

All such choices are deferred to concrete adapter implementations behind the abstract boundaries defined herein.

## 2. System Architecture & Component Boundaries

### 2.1 Layer Hierarchy

The architecture MUST enforce the following pipeline:

```
┌────────────────────────────────────────────────────────┐
│                        Kernel                          │
└───────────────────────────┬────────────────────────────┘
                            │ explicit port (MemoryExecuting / StoragePort)
                            ▼
┌────────────────────────────────────────────────────────┐
│                   Storage Contract                     │
└───────────────────────────┬────────────────────────────┘
                            │
          ┌─────────────────┴─────────────────┐
          ▼                                   ▼
┌───────────────────┐               ┌───────────────────┐
│ Local Persistence │               │ Cloud Persistence │
│   (LocalStore)    │               │   (CloudStore)    │
└─────────┬─────────┘               └─────────┬─────────┘
          │                                   │
          └─────────────────┬─────────────────┘
                            ▼
┌────────────────────────────────────────────────────────┐
│                      Sync Engine                       │
│                      (SyncEngine)                      │
└───────────────────────────┬────────────────────────────┘
                            ▼
┌────────────────────────────────────────────────────────┐
│                  Consistency / Recovery                │
└────────────────────────────────────────────────────────┘
```

### 2.2 Data Flow Prohibition
Direct coupling between Memory/Kernel and Cloud Persistence (`Memory → CloudStore`) MUST NOT exist. Data flow MUST always route through local storage interfaces and the synchronization engine:

```
Memory ──> Storage Contract ──> Local Persistence ──> Sync Engine ──> Cloud Persistence
```

## 3. Strict Ownership & Access Boundaries

1. **Local State Ownership**: `LocalStore` MUST own local persistence. Local storage MUST be the authoritative source of truth for offline agent operations.
2. **Remote State Representation**: `CloudStore` MUST represent remote persistence behind abstract provider boundaries.
3. **Synchronization Authority**: `SyncEngine` MUST be the sole component allowed to orchestrate local ↔ cloud synchronization, execute change queues, detect conflicts, and apply resolved updates.
4. **Subsystem Isolation**:
   * `Kernel` MUST remain completely cloud-agnostic.
   * `PAMemory` MUST remain cloud-agnostic and local-first.
   * `Modules`, `Skills`, `Tools`, `Policy`, and `UI` MUST NOT access `CloudStore` or `SyncEngine` directly.
5. **Dependency Injection**: Storage and synchronization dependencies MUST be injected explicitly via Composition wiring. Service locators, global singletons, or ambient hidden storage state MUST NOT be used.

---

## 4. Identity, Versioning, and Revision Semantics

### 4.1 Record Identity
* Every stored entity MUST possess a globally unique, stable string identity (`id: String`).
* Identity MUST remain immutable across local and remote copies of the record.

### 4.2 Revision & Versioning
* Records MUST carry an explicit logical integer version counter (`version: Int`).
* Records MAY include an explicit content hash or opaque revision token (`revisionToken: String?`) representing the cryptographic checksum or ETag of the payload.

### 4.3 Conflict Authority & Ancestry Boundary
* Timestamps (`updatedAt: Date`) MAY assist in diagnostic logging, telemetry, or heuristic ordering, but timestamps MUST NOT silently act as the sole authority for conflict detection or automated resolution.
* Conflict/divergence MUST be determined from explicit revision/version lineage or an equivalent deterministic revision relation owned by the storage/sync contract.
* A conflict exists if and only if local state and remote state for the same record identity (`id`) diverge in revision lineage without a clear deterministic ancestor relationship.

## 5. Local-First & Synchronization Semantics

### 5.1 Local-First Guarantees
* **Network Independence**: Local storage operations (read, write, delete, query) MUST function seamlessly without active network connectivity or remote server availability.
* **Non-Blocking Execution**: Local persistence operations MUST NEVER block waiting for network responses or remote cloud synchronization.
* **Offline Immunity**: Remote cloud unavailability, network transport errors, or remote server failures MUST NOT invalidate, corrupt, or lock valid local state.

### 5.2 Asynchronous Synchronization & Queueing
* Local state changes MUST be recorded in a durable local sync queue (`enqueueLocalChange(id)`).
* Cloud synchronization MUST execute asynchronously and deferred relative to local state mutations.

### 5.3 Explicit Conflict Policy & Resolution Versioning
* Silent overwrites of divergent state MUST NOT occur (`StorageBoundary.forbidsOverwriteWithoutConflictPolicy = true`).
* When local and remote states diverge, `SyncEngine` MUST construct an explicit `SyncConflict` object.
* Resolution MUST be applied through an explicit `ConflictResolution` policy concept (`keepLocal`, `keepRemote`, `merge`, `requireUser`).
* Every successful conflict resolution MUST produce a new authoritative revision/state, preserving stable record identity and deterministic lineage. The exact mechanism for assigning the next revision/version MUST remain implementation-defined.
* Conflict resolution MUST be deterministic: given identical local record, remote record, and policy, resolution MUST produce identical output state across all nodes.

### 5.4 Idempotency, Durable Recovery, and Fault Tolerance
* Retrying any push, pull, or sync execution MUST be idempotent and MUST NOT duplicate logical records, corrupt indexes, or artificially inflate version counters.
* Recovery and retry operations MUST be durable, bounded, resumable, idempotent, and observable.
* Interrupted synchronization (process termination, power loss, network disconnection mid-sync) MUST resume without corrupting local state, duplicating changes, or losing pending sync records.
* The exact backoff algorithm, retry schedule, and network transition mechanism MUST remain implementation-defined.

## 6. Sub-Milestone Structural Boundaries (M5.1 — M5.5)

Implementation of M5 MUST progress incrementally through these explicit architectural boundaries:

* **M5.1 — Storage Contract & Boundary**: Defines core `StorageRecord`, `LocalStore`, and boundary protocols. Enforces zero import of cloud SDKs into Kernel or Memory.
* **M5.2 — Cloud Persistence**: Establishes `CloudStore` and `CloudStorageProvider` protocols for remote push/pull behind abstract vendor-independent interfaces.
* **M5.3 — Sync Engine**: Implements the `SyncEngine` actor, handling change queueing, version comparison, conflict detection, and `ConflictResolution` execution.
* **M5.4 — Recovery & Consistency**: Implements durable change queue persistence, resumable retry mechanics, offline recovery, and crash-consistency verification without prescribing concrete backoff algorithms.
* **M5.5 — Performance & Integration Gate**: Verifies concurrent operation under high-latency network simulation, large dataset indexing, fault injection, and final architectural integrity audit.

---

## 7. M6+ Boundary Isolation

* M5 MUST NOT introduce user authentication, account identity, OAuth flows, token management, or key material into storage or sync contracts.
* If remote transport requires authorization, M5 contracts MUST depend solely on abstract credential resolver ports provided by `PASecurity`.
* Cognition, agency loops, event replay persistence, and UI modifications MUST NOT be introduced in M5.

---

## 8. Summary of Normative Invariants

1. **Local-first**: Local state MUST remain fully operational without network connectivity.
2. **Cloud is not Kernel**: Kernel MUST NOT depend on or import any cloud provider or network SDK.
3. **No service locator**: All storage dependencies MUST be injected explicitly through Composition.
4. **No global singletons**: Storage ownership MUST be explicit and actor-isolated.
5. **Memory remains independent**: `PAMemory` MUST remain cloud-agnostic.
6. **Sync is a separate capability**: Persistence and synchronization MUST be distinct responsibilities.
7. **Explicit conflicts**: Silent overwrites MUST NOT occur; conflicts MUST be resolved via explicit policy.
8. **Idempotency**: Operation retries MUST produce identical logical state.
9. **Determinism**: Conflict resolution MUST yield identical output given identical inputs.
10. **Observable failure**: Errors MUST NOT be swallowed with `try?` or silent suppressions.
11. **Offline stability**: Network loss MUST NOT corrupt or degrade valid local state.
12. **Versioned state**: Records MUST carry explicit version counters and revision markers.
13. **Vendor isolation**: Cloud implementations MUST live behind abstract adapter boundaries.
14. **No M6 leakage**: Authentication, user accounts, and security secrets MUST NOT leak into storage contracts.
