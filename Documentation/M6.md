# M6 Architecture Contract — Cognition / Agency Integration Gate

Status: M6 Architectural Gate Specification (Normative; M6.0 only)

Milestone baseline: `cf33fb3906621b39e3ef64fa388909432cfadd46` (merged M5 baseline).

This document defines the responsibilities, boundaries, ownership, ordering, evidence flow, and invariants required for M6 implementation. It does not prescribe concrete runtime classes or composition topology.

Normative terms MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL have their RFC 2119 meaning.

---

## 1. Purpose and scope

M6 establishes the contract for integrating Cognition, Agency, Policy, execution, memory, providers, and events so that a goal can progress from perception to an authorized action and back to an evaluated state without ambiguous ownership or control flow.

M6 MUST preserve all valid M0–M5 invariants. M6.0 MUST NOT implement production runtime behavior.

### 1.1 Non-goals

M6 MUST NOT define:

- UI frameworks, screens, or view-model topology.
- Vendor-specific network infrastructure or credentials.
- Third-party agent frameworks.
- Autonomous background daemons.
- Concrete class names, actor topology, or composition-root structure unless required by an invariant.
- M7+ audio streaming, background scheduling, or multi-agent protocols.

---

## 2. M0–M5 forensic baseline

The frozen baseline contains explicit contracts for Cognition artifacts and Agency artifacts but does not yet contain the runtime orchestration required by M6.

Relevant existing contracts include:

- `PACognition`: `Perception`, `ContextBundle`, `ReasoningResult`, `Plan`, `ActionProposal`, `VerificationResult`, `Reflection`, `Planning`, `Executing`, and `CognitionPipelining`.
- `PAAgency`: `Observation`, `Evaluation`, `AgencyLooping`, and `ActionAuthorizing`.
- `PAKernel`: authoritative `AgentState` and goal/lifecycle state.
- `PAPolicy`: policy evaluation and approval boundary.
- `PAModules` / `PATools`: execution boundaries.
- `PAMemory` / `PAStorage`: memory and persistence boundaries.
- `PAEvents`: execution/audit events.

The baseline `CognitionPipelining.run(perception:)` returns only `Reflection`, while `Planning` and `Executing` expose intermediate artifacts separately. The baseline `AgencyLooping.run(goalID:)` returns `Evaluation`, while `Observation` is an Agency artifact. These existing shapes are treated as migration obligations for M6 implementation; M6 MUST NOT pretend that the current API surface already expresses the complete integration contract.

### 2.1 Architectural debt carried into M6

1. Cognition and Agency have contracts but no complete runtime orchestration.
2. Policy enforcement and module capability enforcement are not yet one integrated authorization path.
3. Composition currently wires only a subset of the M6 runtime responsibilities.
4. Provider reasoning is not yet integrated into the goal lifecycle.

These are implementation obligations, not permission to weaken the M6 contract.

## 3. M6 ownership model

Every M6 artifact MUST have one authoritative producer and an explicitly defined consumer boundary.

| Artifact | Producer / authority | Consumers | Authority type |
|---|---|---|---|
| `Perception` | Cognition boundary | Context assembly | Input artifact |
| `ContextBundle` | Cognition context stage | Reasoning | Intermediate artifact |
| `ReasoningResult` | Cognition reasoning stage | Planning | Intermediate artifact |
| `Plan` | Cognition planning stage | Action proposal + Agency | Intermediate artifact; Cognition-owned |
| `ActionProposal` | Cognition proposal stage | Verification + Policy/Agency | Intermediate artifact; Cognition-owned |
| `VerificationResult` | Cognition verification stage | Agency decision path | Evidence artifact; not authoritative AgentState |
| `ActionIntent` | Policy authorization boundary | Execution boundary | Authorized command artifact |
| `Observation` | Agency execution/observation boundary | Evaluation + Cognition feedback | Execution evidence |
| `Evaluation` | Agency evaluation boundary | Adaptation / terminal decision | Agency decision artifact |
| `Reflection` | Cognition reflection stage | State update + next-cycle cognition | Intermediate cognitive artifact |
| `StateUpdate` | Cognition state-update boundary | Authoritative state/memory owners | Mutation request, not independent authority |
| `AgentState` / goal lifecycle | `AgentRuntime` | Whole runtime | **Authoritative state** |

No Cognition or Agency artifact MAY directly become authoritative `AgentState` merely by existing. Durable state mutation MUST cross the owner of that state.

---

## 4. Cross-boundary contract

### 4.1 Cognition → Agency

Cognition MUST expose, directly or through an equivalent contract adapter, the artifacts required by Agency to execute a plan:

`Plan → ActionProposal[] → VerificationResult`

The Agency boundary MUST receive enough information to identify the goal, plan, action, required capability, and verification outcome without accessing Cognition internals.

Agency MUST NOT inspect Cognition implementation state, provider state, memory internals, or private pipeline stages.

### 4.2 Agency → Cognition

After execution, Agency MUST return execution evidence to Cognition as:

`Observation[] + Evaluation`

The feedback MUST identify the affected action/plan/goal and whether execution succeeded. Cognition MAY use that evidence to produce `Reflection` and determine whether another cognitive cycle is required.

The feedback loop MUST be explicit. It MUST NOT be an implicit call into a hidden Cognition stage.

### 4.3 Policy boundary

Before an action crosses into execution, `ActionProposal` MUST pass through the Policy authorization boundary and produce an authorized `ActionIntent` or an explicit denial/rejection.

Policy MUST NOT be bypassed by Cognition, Agency, Tools, Skills, Modules, or Providers.

---

## 5. Normative end-to-end ordering

The canonical M6 control flow is:

```text
Perception
  → Context
  → Reasoning
  → Planning
  → ActionProposal
  → Verification
  → Policy Authorization
  → Execution
  → Observation
  → Evaluation
  → Reflection
  → StateUpdate
  → Continue / Complete / Abort
```

This ordering resolves the previous ambiguity: **Reflection is post-execution**, not a pre-execution cognition stage.

### 5.1 Repeat / branch rules

- Planning MAY produce zero or more executable proposals. Zero proposals MUST NOT be treated as successful execution.
- Verification rejection MUST prevent the affected proposal from reaching execution.
- Policy denial or approval failure MUST prevent the affected intent from reaching execution.
- Execution MAY produce multiple observations for multiple authorized actions.
- Evaluation MAY select `continue`, `complete`, or `abort`.
- `continue` MUST feed `Observation + Evaluation` into a new Cognition cycle; it MUST NOT jump directly back into an arbitrary internal stage.
- `complete` MUST terminate the current goal execution cycle after required state/event persistence succeeds.
- `abort` MUST terminate the current goal execution cycle fail-closed while preserving required evidence.
- Reflection MAY request adaptation, but adaptation MUST re-enter through the defined Cognition cycle rather than mutating Agency internals.

### 5.2 No hidden execution

Cognition MUST NOT execute actions merely because it generated an `ActionProposal`.

Agency MUST NOT manufacture a new plan without crossing the Cognition planning boundary.

Execution MUST NOT occur without Policy authorization where authorization is required.

## 6. StateUpdate and durable-state authority

`StateUpdate` is a **mutation request/artifact**, not a second state authority.

The owner of each durable state domain MUST validate and commit the update:

- `AgentState` and goal/lifecycle state: `AgentRuntime`.
- Memory records: `PAMemory` / its persistence owner.
- Audit events: `PAEvents`.
- Sync state: existing synchronization owner.

A StateUpdate MUST identify its source evidence and MUST NOT mutate authoritative state without the owning boundary accepting it.

At minimum, a durable update MUST be supported by the relevant `Reflection`, `Observation`, `Evaluation`, or other explicitly defined evidence. Unsupported or ambiguous mutations MUST fail closed.

Cognition and Agency MUST NOT directly mutate `AgentRuntime` lifecycle state. Terminal goal transitions remain owned by `AgentRuntime` based on the Agency evaluation result.

---

## 7. Concurrency and failure semantics

- Authoritative `AgentState` and goal lifecycle mutation MUST remain serialized by its owner.
- Runtime components MUST respect existing Swift actor / `Sendable` isolation contracts.
- Equivalent concurrent executions MUST NOT create conflicting authoritative state commits.
- Errors in context, reasoning, verification, authorization, execution, observation, evaluation, reflection, or persistence MUST NOT be silently swallowed.
- A failed active execution MUST preserve enough evidence to explain the failure and leave authoritative state consistent.
- Partial execution MUST NOT be reported as successful completion.

---

## 8. Auditability and provenance

Every M6 execution cycle MUST preserve a trace/session identity across its artifacts and events.

At minimum, policy decisions, authorization attempts, execution attempts, observations, evaluations, and terminal outcomes MUST be auditable through the existing event boundary.

Secrets and credential material MUST NOT enter cognitive artifacts or audit events.

---

## 9. Dependency direction

M6 preserves the M0–M5 rule that dependencies are resolved explicitly through Composition and concrete implementations remain behind their existing module boundaries.

M6 defines **responsibility**, not a mandatory class graph.

In particular:

- Cognition owns cognitive artifact production.
- Agency owns execution-loop coordination and evaluation.
- Policy owns authorization decisions.
- Execution boundaries own actual module/tool execution.
- Memory owns memory persistence.
- `AgentRuntime` owns authoritative lifecycle/state mutation.
- Composition owns dependency assembly.

No component may acquire another component through a service locator or global singleton.

---

## 10. M6 implementation obligations

M6.1+ MUST reconcile the existing contracts with this normative boundary. This includes, where necessary, introducing adapters or revised protocol surfaces so that:

1. Cognition can expose the artifacts required by Agency.
2. Agency can return execution evidence to Cognition.
3. Policy authorization is on the execution path.
4. Reflection is generated from post-execution evidence.
5. StateUpdate cannot become an independent state authority.
6. Goal/lifecycle mutation remains owned by `AgentRuntime`.
7. Composition explicitly wires the required responsibilities.

These are obligations to satisfy the contract, not prescribed class names.

---

## 11. Verification gate for M6.1

Before M6.1 is considered complete, tests MUST demonstrate:

1. `Plan` and `ActionProposal` cross the Cognition → Agency boundary explicitly.
2. Verification rejection prevents execution.
3. Policy denial/approval failure prevents execution.
4. Execution produces `Observation` and `Evaluation`.
5. `Observation + Evaluation` re-enter Cognition only through the defined feedback boundary.
6. Reflection is post-execution.
7. StateUpdate cannot directly mutate authoritative AgentState without its owner.
8. `continue` creates a new defined cognition cycle; `complete` and `abort` terminate deterministically.
9. Failures preserve invariants and required audit evidence.
10. Forbidden dependency/import boundaries remain intact.

---

## 12. M7+ boundary

M7+ may extend the system with UI evolution, background scheduling, real-time modalities, richer multi-agent coordination, or external infrastructure, but MUST NOT silently redefine the M6 ownership and cross-boundary invariants.

---

## 13. M6.0 gate

M6.0 is documentation and architectural contract only.

No production implementation, runtime refactor, concrete orchestrator, or speculative abstraction is introduced by this milestone gate.

The acceptance criterion is:

> A separate engineer can implement Cognition + Agency from this document without guessing artifact ownership, cross-boundary inputs/outputs, execution ordering, feedback semantics, or durable-state authority.
