# M7 Architecture Contract — Durable Run Lifecycle, Checkpointing, Interruption Recovery & Capability Bounding

Status: M7 Architectural Gate Specification (Normative; M7.0 only)

Milestone baseline: M6 baseline (merged M6 composition and semantics baseline).

This document defines the responsibilities, boundaries, ownership, control flow, evidence model, failure/recovery semantics, concurrency model, and dependency architecture required for M7 implementation. It establishes the architectural contract for durable agent execution runs, execution checkpoints, capability leasing, and interruption recovery.

Normative terms MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL have their RFC 2119 meaning.

---

## 1. Scope

M6 established the integrated cognitive cycle (Perception → Context → Reasoning → Planning → ActionProposal → Verification → Policy Authorization → Execution → Observation → Evaluation → Reflection → StateUpdate). However, M6 orchestration operates imperatively in-memory within single goal execution cycles.

M7 extends the system with:
1. **Durable Run & Session Lifecycle**: Bounding goal execution within explicit, persistent execution runs (`RunID`, `RunRecord`, `RunState`).
2. **First-Class Execution Attempts**: Tracking tool/action invocation through a durable `ExecutionAttempt` with status `NOT_STARTED`, `STARTED_UNKNOWN`, `COMPLETED`, or `FAILED`.
3. **Structured Execution Checkpointing**: Persisting transactional execution state (`RunCheckpoint`) before and after execution stages.
4. **Interruption Recovery Engine**: Safely re-hydrating or resuming interrupted or crashed execution runs fail-closed based on verifiable checkpoint and execution evidence.
5. **StateUpdate ↔ EventLog Transaction Protocol**: Resolving Issue #23 with a durable write-ahead journal protocol for state mutation and audit logging atomicity.
6. **Capability Leasing**: Applying time-bound and step-bound capability leases before policy authorization to enforce execution budget boundaries.
7. **Correlated Provenance & Extended Audit**: Correlating `RunID`, `SessionID`, `TraceID`, `GoalID`, `ExecutionAttemptID`, and `ActionID` across execution events.

M7 MUST preserve all valid M0–M6 invariants.

### 1.1 Non-goals

M7 MUST NOT define or introduce:
- Production M7 runtime implementation code in M7.0 (M7.0 is architecture specification ONLY).
- A second authority for `AgentState` or goal lifecycle (`AgentRuntime` remains the sole authority).
- Bypassing Policy or `ApprovalGate`.
- Direct UI bindings or SwiftUI view-model dependencies in Kernel.
- Autonomous multi-tenant cloud orchestration daemons or vendor SDKs in Kernel.
- Swallowing errors or performing unverified implicit recovery.
- Credential material in run records, checkpoints, cognitive artifacts, events, or logs.

## 2. Ownership / Authority

Every M7 artifact MUST have exactly one authoritative producer and owner.

### 2.1 Canonical Ownership Table

| Artifact | Producer / Authority | Consumers | Durable? | Authority Scope |
|---|---|---|---|---|
| `RunID` | Run Boundary / Orchestrator | Events, Checkpoints, Audit, Recovery | Yes (Value) | Execution run identity |
| `RunRecord` | Run Lifecycle Owner | `AgentRuntime`, Recovery Engine, Audit | Yes (Store backed) | Execution run metadata & state |
| `ExecutionAttempt` | Execution Boundary | Recovery Engine, Audit, Orchestrator | Yes (Store backed) | Side-effect invocation status |
| `ExecutionReceipt` | Target Module / Provider | Execution Boundary, Recovery Engine | Yes (Store backed) | External side-effect evidence |
| `RunCheckpoint` | Checkpoint Stage | Recovery Engine, Orchestrator | Yes (Store backed) | Logical orchestration snapshot |
| `CapabilityLease` | Capability Governor / Policy | Agency Execution | Transient (Memory) | Bounded execution permission |
| `StateJournalEntry` | Transaction Protocol | `AgentRuntime`, `EventLog`, Recovery Engine | Yes (Store backed) | StateUpdate write-ahead log |
| `ExecutionEvent` | Kernel / Orchestrator | `EventLog` | Yes (EventLog) | Immutable append-only audit evidence |
| `AgentState` / `Goal` | `AgentRuntime` | Whole System | **Authoritative State** | **Sole system state authority** |

### 2.2 Checkpoint Snapshot vs. Durable Execution Evidence

M7 explicitly separates logical orchestration checkpoints from side-effect execution evidence:
- **Checkpoint Snapshot**: A recovery snapshot describing logical orchestration state (pending proposals, cycle index, last verified evaluation). A checkpoint MUST NOT be treated as proof that an external side effect did or did not occur.
- **Durable Execution Evidence**: Evidence describing what actually happened at the execution boundary (`ExecutionAttempt`, `ExecutionReceipt`, `Observation`).

### 2.3 Authoritative Artifact Matrix

To eliminate ambiguity during execution and recovery, the following table defines which artifact is authoritative for every operational question:

| Question | Authoritative Artifact | Non-Authoritative Artifact |
|---|---|---|
| "Was an action proposed?" | `ActionProposal` in `RunCheckpoint` / EventLog | Module runtime state |
| "Was execution authorized?" | `ActionIntent` + Policy Decision Event (`actionAuthorized`) | `ActionProposal` alone |
| "Did execution start?" | `ExecutionAttempt` (`STARTED_UNKNOWN` or `COMPLETED`) | Pre-execution `RunCheckpoint` |
| "Did execution finish?" | `ExecutionAttempt` (`COMPLETED`/`FAILED`) + `ExecutionReceipt` | `ActionIntent` |
| "Did external side effect become durable?" | `ExecutionReceipt` from target module/system | `RunCheckpoint` or `Observation` |
| "Was an observation persisted?" | `Observation` record in `RunCheckpoint` / EventLog | Module output string |
| "Was StateUpdate committed?" | `AgentRuntime` `GoalStatus` | `StateJournalEntry` alone or `Evaluation` |

## 3. Lifecycle State Model

The M7 execution pipeline is modeled as a formal deterministic state machine:

```text
Run → Cycle → Action → ExecutionAttempt → Observation → StateUpdate → Audit
```

For every state transition, preconditions, durable evidence, failure windows, and recovery decisions MUST be explicitly defined:

### 3.1 State Transitions Table

| Transition | Precondition | Durable Evidence Generated | Failure Window | Recovery Decision |
|---|---|---|---|---|
| **Run Initialized** | Valid `GoalID`, Goal in `AgentRuntime` is `.active` or `.proposed` | `RunRecord(status: .initialized)` + Event `runInitialized` | Disk write fails or EventLog throws | Halt run initialization fail-closed; Goal status remains unchanged |
| **Cycle Started** | `RunRecord` in `.initialized` or `.running` | Event `perceptionReceived` + `contextBuilt` | Context assembly or EventLog throws | Retry cycle or transition `RunRecord` to `.failed` |
| **Proposal Verified** | `Plan` generated, proposals verified | Pre-execution `RunCheckpoint` saved | Checkpoint store write fails | Abort cycle before Policy authorization; zero tool calls executed |
| **Attempt Initialized** | Proposal verified, `CapabilityLease` valid | `ExecutionAttempt(status: .NOT_STARTED)` | ExecutionAttemptStore write fails | Halt execution before side effect starts; Attempt stays `.NOT_STARTED` |
| **Attempt Started** | Policy authorized, lease step consumed | `ExecutionAttempt(status: .STARTED_UNKNOWN)` | Process crash mid-invocation | On recovery, query target receipt to resolve `.STARTED_UNKNOWN` |
| **Attempt Completed** | Target module returns result | `ExecutionAttempt(status: .COMPLETED)` + `ExecutionReceipt` | Receipt write fails | On recovery, receipt check confirms side effect complete; skip re-execution |
| **Observation Persisted** | Attempt completed or failed | `Observation` recorded in post-execution `RunCheckpoint` | Post-execution checkpoint write fails | Recover `Observation` from `ExecutionReceipt` without re-executing action |
| **StateUpdate Prepared** | Evaluation & Reflection complete | `StateJournalEntry(status: .prepared)` persisted | Journal write fails | Abort state update; Goal status stays in previous valid state |
| **State Committed** | Journal prepared | `AgentRuntime` updates `GoalStatus` | `AgentRuntime` state update throws | Roll back journal to `.prepared` / `.aborted` |
| **Audit Committed** | State committed | Event `stateUpdated` appended to `EventLog` | EventLog throws | Re-try event append via journal recovery protocol |
| **Transaction Finalized** | Audit committed | `StateJournalEntry(status: .finalized)` | Finalize write fails | Journal recovery completes finalization without re-applying state |
| **Run Completed** | State update finalized | `RunRecord(status: .completed)` | RunRecord write fails | Re-assert `.completed` on run record reconciliation |

## 5. Execution Attempt Contract

### 5.1 First-Class Identity & Lifecycle
Every tool or module execution MUST be assigned a unique `ExecutionAttemptID` and an `idempotencyKey` derived deterministically:
`idempotencyKey = SHA256(RunID + GoalID + CycleIndex + ActionID + ToolID)`

The attempt lifecycle progresses through strict stages:
1. `NOT_STARTED`: Attempt record created on disk before invocation.
2. `STARTED_UNKNOWN`: Attempt updated on disk immediately prior to module dispatch.
3. `COMPLETED`: Attempt updated on disk with `receiptRef` after target module execution returns.
4. `FAILED`: Attempt updated on disk after target module execution throws or times out.

### 5.2 Resolution of `STARTED_UNKNOWN`
If process crashes while an attempt is in `STARTED_UNKNOWN` status:
- The recovery engine MUST NOT blindly execute the action again.
- The recovery engine MUST query the target module runtime or external provider using `idempotencyKey` to check if an `ExecutionReceipt` exists.
- If `ExecutionReceipt` exists: status is transitioned to `COMPLETED`, and `Observation` is synthesized from the receipt without re-executing the action.
- If `ExecutionReceipt` does NOT exist and target module is non-idempotent: status is transitioned to `FAILED`, and `Observation(succeeded: false)` is recorded. Side effect MUST NOT be re-executed.
- If target module explicitly supports idempotent re-execution: policy authorization MUST be re-verified before re-executing.

### 5.3 Explicit Execution Semantics
- **Non-Idempotent / External Side-Effect Capabilities** (`.write`, `.execute`, external network calls): Enforce **at-most-once** execution semantics. In `STARTED_UNKNOWN` without verifiable receipt, re-execution is forbidden.
- **Idempotent Read-Only Capabilities** (`.read`): Enforce **at-least-once with mandatory idempotency key check**.

## 6. Checkpoint Contract

1. **Pre-Execution Checkpoint**: Captured after proposal verification and stored to `RunCheckpointStore` before Policy authorization or `ExecutionAttempt` initialization.
2. **Post-Execution Checkpoint**: Captured after module execution and `Observation` generation, recording updated `completedObservations` and cycle status.
3. **Snapshot Isolation**: Checkpoints represent logical orchestrator progress. Recovery MUST cross-reference `RunCheckpoint` with `ExecutionAttemptStore` and `AgentRuntime` before resuming execution.

---

## 7. Execution Evidence Contract

Side-effect evidence MUST be backed by a durable `ExecutionReceipt` generated by or registered with the target execution module:
- `ExecutionReceipt` MUST contain `receiptID`, `attemptID`, `toolID`, `idempotencyKey`, and `timestamp`.
- An `Observation(succeeded: true)` referencing a tool execution MUST be supported by an `ExecutionReceipt`.
- If an `ExecutionReceipt` is present on disk, side-effect completion is authoritative even if `Observation` or post-execution `RunCheckpoint` write failed.

## 8. StateUpdate Transaction Protocol

To eliminate state/audit divergence (Issue #23) without relying on infallible in-memory rollback, M7 specifies a **Durable Write-Ahead Journal Protocol**:

```text
Orchestrator
      │
      │ 1. Prepare StateJournalEntry(status: .prepared)
      ▼
StateJournalStore (Persisted to disk)
      │
      │ 2. Commit GoalStatus in AgentRuntime
      ▼
AgentRuntime GoalStore
      │
      │ 3. Append Event (.stateUpdated)
      ▼
EventLog
      │
      │ 4. Mark StateJournalEntry(status: .finalized)
      ▼
StateJournalStore
```

### 8.1 Protocol Rules & Recovery Matrix

| Failure Point | State Store Condition | EventLog Condition | Recovery Mechanism | Final State |
|---|---|---|---|---|
| **Failure during Journal Prepare** | `GoalStatus` unchanged | Event not written | Transaction aborted; throw error | Goal status remains intact in previous state |
| **Failure during State Commit** | `StateJournalEntry` is `.prepared`; `AgentRuntime` unchanged | Event not written | On recovery, journal entry is marked `.aborted` | Goal status remains intact in previous state |
| **State Commit succeeds, EventLog fails** | `StateJournalEntry` is `.prepared`; `AgentRuntime` updated | Event append threw | Recovery engine inspects `.prepared` journal, re-emits `.stateUpdated` event, then finalizes journal | Goal status committed; Event appended fail-closed |
| **EventLog succeeds, Finalize fails** | `StateJournalEntry` is `.stateCommitted`; `AgentRuntime` updated | Event appended | Recovery engine detects `.stateCommitted` or `.prepared` with event present; marks journal `.finalized` | Goal status committed; no duplicate event emitted |
| **Rollback of State Commit fails** | `AgentRuntime` updated, EventLog failed, disk corrupt | EventLog missing | Recovery engine detects un-finalized journal; forces re-emission of `.stateUpdated` event to restore audit consistency | State and audit log aligned |

## 9. Recovery Decision Matrix

When `RunRecoveryEngine` boots or scans unclosed runs on process restart, it evaluates durable evidence against this deterministic decision matrix:

| ExecutionAttempt Status | ExecutionReceipt | Observation in Checkpoint | GoalStatus in AgentRuntime | Recovery Decision |
|---|---|---|---|---|
| **No Attempt** | Absent | Absent | `.active` | Safe to start action subject to Policy & Lease check |
| **`NOT_STARTED`** | Absent | Absent | `.active` | Safe to start action subject to Policy & Lease check |
| **`STARTED_UNKNOWN`** | **Present** | Absent | `.active` | Do NOT re-execute tool. Synthesize `Observation(succeeded: true)` from receipt, persist post-execution checkpoint, resume evaluation. |
| **`STARTED_UNKNOWN`** | **Absent (Non-idempotent)** | Absent | `.active` | Do NOT re-execute tool. Record `Observation(succeeded: false, reason: "Interrupted execution, receipt unverified")`, submit `StateUpdate(.aborted)`. |
| **`STARTED_UNKNOWN`** | **Absent (Idempotent)** | Absent | `.active` | Re-verify Policy authorization & CapabilityLease; re-execute action if authorized. |
| **`COMPLETED`** | Present | Present | `.active` | Do NOT re-execute tool. Resume cycle from post-execution checkpoint. |
| **`COMPLETED`** | Present | **Absent** | `.active` | Do NOT re-execute tool. Re-hydrate `Observation` from receipt, persist checkpoint, resume evaluation. |
| **Any Status** | Any | Any | **`.completed`** | Do NOT execute tool. Reconcile `RunRecord.status = .completed`, finalize state journal. |
| **Any Status** | Any | Any | **`.aborted`** | Do NOT execute tool. Reconcile `RunRecord.status = .failed` or `.interrupted`. |
| **Corrupt Checkpoint** | N/A | N/A | `.active` | Fail closed. Transition `RunRecord.status = .failed`, submit `StateUpdate(.aborted)`. |
| **Lease Expired** | N/A | N/A | `.active` | Re-evaluate Policy for fresh CapabilityLease. If denied, fail proposal execution. |

## 10. RunState ↔ GoalState Mapping

`AgentRuntime` remains the sole authority for `AgentState` and `GoalStatus`. `RunRecord.status` tracks execution run progress and MUST reconcile cleanly with `AgentRuntime`:

| `AgentRuntime` `GoalStatus` | `RunRecord.status` | Reconciliation Rules & Priority |
|---|---|---|
| `.proposed` | `.initialized` | Run registered; goal awaiting activation. |
| `.active` | `.running` / `.checkpointed` | Run executing active cognitive cycles. |
| `.completed` | `.completed` | Goal completed in `AgentRuntime`. `RunRecord` MUST be set to `.completed`. |
| `.aborted` | `.failed` / `.interrupted` | Goal aborted in `AgentRuntime`. `RunRecord` MUST be set to `.failed` or `.interrupted`. |
| `.blocked` | `.paused` | Goal paused/blocked in `AgentRuntime`. `RunRecord` MUST be set to `.paused`. |

### 10.1 Conflict Resolution Invariants
1. If `AgentRuntime` indicates `.completed` or `.aborted`, but `RunRecord` indicates `.running`, `AgentRuntime` status takes precedence. `RunRecord` MUST transition to `.completed` or `.failed` without executing side effects.
2. `RunLifecycleManager` MUST NOT mutate `AgentRuntime` goal state directly. It MUST request state updates via `AgentRuntime.applyStateUpdate(_:)`.

## 11. CapabilityLease Contract

`CapabilityLease` defines dynamic time-bounded and step-bounded execution limits:

### 11.1 Behavioral Specifications
- **Lease Owner**: Granted per `RunID` by Policy / Capability Governor.
- **Run Ownership**: A lease is strictly bound to a single `RunID`. Leases MUST NOT cross run boundaries.
- **Atomic Step Consumption**: Step consumption `consume(step)` MUST be atomic.
- **Max-Step Invariant**: `consume(step)` MUST enforce `currentStepCount + step <= maxStepCount`. If `currentStepCount + step > maxStepCount`, `consume` MUST throw `CapabilityLeaseError.maxStepsExceeded` and deny execution.
- **Expiration Check**: `isExpired` evaluates `currentTime >= expiresAt`. An expired lease MUST evaluate as invalid and deny execution.
- **Revocation**: A lease MAY be explicitly revoked. A revoked lease MUST deny all subsequent step consumptions.
- **Concurrent Consume Behavior**: Concurrent `consume` operations on the same lease MUST be serialized atomically (e.g. within actor isolation). Concurrent requests MUST NOT race to exceed `maxStepCount`.
- **Termination Behavior**: Upon run termination (`.completed`, `.failed`, `.aborted`), any active lease for that `RunID` is automatically invalidated.

## 12. Failure Semantics

M7 enforces strict fail-closed classification across all failure domains:

1. **Transient Execution Failure**: Tool timeout or network error. Recorded in `Observation(succeeded: false)`. Cycle evaluation decides whether to `.continue` or `.abort`.
2. **Permanent Execution Failure**: Unregistered tool ID or schema validation failure. Recorded in `Observation(succeeded: false)`. Evaluation returns `.abort`.
3. **Interrupted Execution**: Process crash during cycle. On boot, `RunRecoveryEngine` executes the Recovery Decision Matrix using durable `ExecutionAttempt` and `ExecutionReceipt` evidence.
4. **Persistence Failure**: Disk write fails for Checkpoint, ExecutionAttempt, or Journal. Execution cycle halts fail-closed before dispatching side effects.
5. **Audit/Event Failure**: `EventLog.append` throws. StateJournal protocol recovers audit consistency fail-closed.
6. **Recovery Failure**: Checkpoint or attempt store is corrupt/unreadable. Recovery engine transitions `RunRecord` to `.failed` and requests goal abort.

## 13. Security / Secret Isolation

1. **Credential Isolation**: Secrets, API keys, bearer tokens, and credentials MUST NOT be stored in `RunRecord`, `RunCheckpoint`, `ExecutionAttempt`, `ExecutionReceipt`, `StateJournalEntry`, `ExecutionEvent`, or log metadata.
2. **Redaction Boundary**: Tool parameters or payloads containing authorization fields MUST be redacted prior to persisting checkpoints, receipts, or audit events.
3. **Lease Isolation**: `CapabilityLease` permissions are scoped strictly to the authorized `RunID` and cannot be hijacked by concurrent runs.

---

## 14. Concurrency

1. **Actor Boundaries**:
   - `AgentRuntime`: Actor owning `AgentState` and `GoalStore`.
   - `RunLifecycleOwner`: Actor owning `RunRecord` and run status progression.
   - `ExecutionBoundary`: Actor managing `ExecutionAttempt` lifecycle and receipt verification.
   - `RecoveryEngine`: Actor orchestrating crash recovery workflows.
2. **Sendable Isolation**: All contracts, artifacts, receipts, and events MUST conform to `Sendable`.
3. **Multi-Run Isolation**: Concurrent runs MUST operate on distinct `RunID`s and distinct `GoalID`s. Two concurrent runs MUST NOT mutate the same goal or lease.

## 15. Verification Matrix

The M7 specification defines explicit, observable verification test specifications covering all recovery and failure windows:

| Invariant / Feature | Failure Injected | Expected Durable Evidence | Expected Recovery Decision | Forbidden Outcome |
|---|---|---|---|---|
| **1. Crash Before Execution** | Process killed before `ExecutionAttempt` created | Pre-execution checkpoint on disk; no `ExecutionAttempt` | Attempt `NOT_STARTED`; safe to re-verify & start | Executing tool without Policy re-verification |
| **2. Crash After Execution Start** | Process killed during tool execution | `ExecutionAttempt(status: .STARTED_UNKNOWN)` | Query receipt; if absent & non-idempotent, mark failed & abort | Re-executing non-idempotent tool blindly |
| **3. Crash After External Completion** | Process killed after module finished, before post-checkpoint | `ExecutionAttempt` + `ExecutionReceipt` on disk | Synthesize `Observation` from receipt; resume evaluation | Re-executing completed tool |
| **4. Missing Observation** | Post-execution checkpoint write failed | `ExecutionReceipt` present; Checkpoint missing observation | Re-hydrate `Observation` from receipt; persist checkpoint | Re-executing tool or aborting valid execution |
| **5. Missing Event** | EventLog threw during cycle transition | Checkpoint present; Event missing | Re-emit missing `ExecutionEvent` from journal | Divergence between AgentState and EventLog |
| **6. State Persistence Failure** | StateJournalStore disk write failed | Journal write failed; `AgentRuntime` unchanged | Abort StateUpdate; Goal remains in previous state | Goal status changing in `AgentRuntime` |
| **7. Event Persistence Failure** | EventLog threw during `StateUpdate` | Journal `.prepared`; `AgentRuntime` committed | Journal recovery re-emits `.stateUpdated` event | Goal committed without audit event |
| **8. Corrupt Checkpoint** | Checkpoint snapshot file corrupted on disk | Corrupt file on disk | Mark `RunRecord` `.failed`; submit `StateUpdate(.aborted)` | Executing action from corrupt checkpoint |
| **9. Expired Capability Lease** | System clock advanced past `expiresAt` | `CapabilityLease(expiresAt < now)` | Policy denies execution; record `Observation(succeeded: false)` | Executing action on expired lease |
| **10. Concurrent Lease Consumption** | 2 concurrent tasks consume last step | `currentStepCount = maxStepCount` | First task succeeds; second throws `maxStepsExceeded` | `currentStepCount > maxStepCount` |
| **11. Already-Completed Goal** | Process crashed; Goal completed in AgentRuntime, RunRecord `.running` | AgentRuntime goal `.completed` | Reconcile `RunRecord.status = .completed` without tool execution | Executing tool on completed goal |
| **12. Already-Aborted Goal** | Process crashed; Goal aborted in AgentRuntime, RunRecord `.running` | AgentRuntime goal `.aborted` | Reconcile `RunRecord.status = .failed` without tool execution | Executing tool on aborted goal |
| **13. Duplicate Recovery Attempt** | Recovery engine invoked twice concurrently | `RunRecord(status: .recovering)` | Second invocation waits or returns idempotent result | Duplicate state updates or tool executions |

## 16. M7.1 Implementation Boundary

M7.0 freezes behavioral contracts, invariants, recovery matrices, and state protocols. The following implementation decisions remain unfrozen for M7.1+:
- Concrete file formats for `RunStore`, `ExecutionAttemptStore`, and `StateJournalStore` (e.g. JSON, SQLite, or atomic sidecar files).
- Internal class/actor layout of orchestrators and recovery engines, provided they satisfy all protocol boundaries and ownership rules.
- Concrete timer implementation for lease expiration checks.

---

## 17. M8+ Boundary

M8+ may introduce multi-agent network protocols, real-time audio streaming, background system daemons, or remote synchronization protocol extensions, but MUST NOT alter M7 durable execution attempts, checkpointing, StateUpdate transaction protocols, or recovery semantics.
