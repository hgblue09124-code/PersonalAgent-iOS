# M7 Architecture Contract — Durable Run Lifecycle, Checkpointing, Interruption Recovery & Capability Bounding

Status: M7 Architectural Gate Specification (Normative; M7.0 only)

Milestone baseline: M6 baseline (merged M6 composition and semantics baseline).

This document defines the responsibilities, boundaries, ownership, control flow, evidence model, failure/recovery semantics, concurrency model, and dependency architecture required for M7 implementation. It establishes the architectural contract for durable agent execution runs, execution checkpoints, capability leasing, and interruption recovery.

Normative terms MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL have their RFC 2119 meaning.

---

## 1. Scope

M6 established the integrated cognitive cycle (Perception → Context → Reasoning → Planning → ActionProposal → Verification → Policy Authorization → Execution → Observation → Evaluation → Reflection → StateUpdate). However, M6 orchestration operates imperatively in-memory within single goal execution cycles.

M7 extends the system with:
1. **Durable Run & Session Lifecycle**: Bounding goal execution within explicit, persistent execution runs (`RunID`, `RunRecord`, `RunState`).
2. **First-Class Execution Attempts & Evidence Resolution**: Tracking tool/action invocation through a durable `ExecutionAttempt` with status `NOT_STARTED`, `STARTED_UNKNOWN`, `COMPLETED`, `FAILED`, or `UNRESOLVED`, and resolving execution truth via a normative `ExecutionEvidenceResolver` contract.
3. **Structured Execution Checkpointing**: Persisting transactional execution state (`RunCheckpoint`) before and after execution stages.
4. **Interruption Recovery Engine**: Safely re-hydrating or resuming interrupted or crashed execution runs fail-closed based on verifiable checkpoint and execution evidence.
5. **StateUpdate ↔ EventLog Transaction Protocol & Stable EventID**: Resolving Issue #23 with a durable write-ahead journal protocol for state mutation and audit logging atomicity using stable, idempotent event identity.
6. **Capability Leasing**: Applying time-bound and step-bound capability leases before policy authorization to enforce execution budget boundaries.
7. **Correlated Provenance & Extended Audit**: Correlating `RunID`, `SessionID`, `TraceID`, `GoalID`, `ExecutionAttemptID`, `EventID`, and `ActionID` across execution events.

M7 MUST preserve all valid M0–M6 invariants.

### 1.1 Core Execution & Recovery Semantic Principles

To ensure safety and determinism during recovery, M7 freezes the following core semantic principles:
- **`UNKNOWN ≠ FAILED`**: A lack of execution receipt or status update does NOT indicate that an execution failed.
- **`UNKNOWN ≠ NOT_STARTED`**: An unknown execution state MUST NOT be treated as if execution never began.
- **`UNAVAILABLE ≠ NOT_STARTED`**: Unavailability of an evidence resolution mechanism MUST NOT be interpreted as proof that an action was not started.
- **Absence of Evidence is Not Evidence of Absence/Failure**: The system MUST NOT synthesize a failed `Observation(succeeded: false)` or a successful `Observation(succeeded: true)` without verifiable evidence.
- **No Unverified Re-execution**: Potentially completed side effects MUST NOT be blindly retried. If execution truth cannot be resolved for a non-idempotent capability, recovery MUST fail closed or enter an explicitly defined unresolved terminal disposition (`RunRecord.status = .interrupted` or `.failed` with unresolved state metadata).
- **Stable Event Identity**: Retries of event logging MUST reuse the original, durably persisted `EventID` to guarantee idempotent audit logging without duplicate entries.

### 1.2 Non-goals

M7 MUST NOT define or introduce:
- Production M7 runtime implementation code in M7.0 (M7.0 is architecture specification ONLY).
- A second authority for `AgentState` or goal lifecycle (`AgentRuntime` remains the sole authority).
- Bypassing Policy or `ApprovalGate`.
- Direct UI bindings or SwiftUI view-model dependencies in Kernel.
- Autonomous multi-tenant cloud orchestration daemons or vendor SDKs in Kernel.
- Swallowing errors or performing unverified implicit recovery.
- Credential material in run records, checkpoints, cognitive artifacts, events, or logs.
- Automatic or blind retry of non-idempotent side effects with unresolved execution state.
- Generating new `EventID`s during WAL journal recovery retries.

## 2. Ownership / Authority

Every M7 artifact MUST have exactly one authoritative producer and owner.

### 2.1 Canonical Ownership Table

| Artifact | Producer / Authority | Consumers | Durable? | Authority Scope |
|---|---|---|---|---|
| `RunID` | Run Boundary / Orchestrator | Events, Checkpoints, Audit, Recovery | Yes (Value) | Execution run identity |
| `RunRecord` | Run Lifecycle Owner | `AgentRuntime`, Recovery Engine, Audit | Yes (Store backed) | Execution run metadata & state |
| `ExecutionAttempt` | Execution Boundary | Recovery Engine, Audit, Orchestrator | Yes (Store backed) | Side-effect invocation status |
| `ExecutionReceipt` | Target Module / Provider | Execution Boundary, Recovery Engine | Yes (Store backed) | External side-effect evidence |
| `ExecutionEvidenceResolver` | Target System / Evidence Boundary | Recovery Engine, Execution Boundary | N/A (Contract) | Authoritative evidence resolution |
| `RunCheckpoint` | Checkpoint Stage | Recovery Engine, Orchestrator | Yes (Store backed) | Logical orchestration snapshot |
| `CapabilityLease` | Capability Governor / Policy | Agency Execution | Transient (Memory) | Bounded execution permission |
| `StateJournalEntry` | Transaction Protocol | `AgentRuntime`, `EventLog`, Recovery Engine | Yes (Store backed) | StateUpdate write-ahead log & stable `EventID` binding |
| `ExecutionEvent` | Kernel / Orchestrator | `EventLog` | Yes (EventLog) | Immutable append-only audit evidence |
| `AgentState` / `Goal` | `AgentRuntime` | Whole System | **Authoritative State** | **Sole system state authority** |

### 2.2 Checkpoint Snapshot vs. Durable Execution Evidence

M7 explicitly separates logical orchestration checkpoints from side-effect execution evidence:
- **Checkpoint Snapshot**: A recovery snapshot describing logical orchestration state (pending proposals, cycle index, last verified evaluation). A checkpoint MUST NOT be treated as proof that an external side effect did or did not occur.
- **Durable Execution Evidence**: Evidence describing what actually happened at the execution boundary (`ExecutionAttempt`, `ExecutionReceipt`, `Observation`, and `EvidenceResolution`).

### 2.3 Authoritative Artifact Matrix

To eliminate ambiguity during execution and recovery, the following table defines which artifact is authoritative for every operational question:

| Question | Authoritative Artifact | Non-Authoritative Artifact |
|---|---|---|
| "Was an action proposed?" | `ActionProposal` in `RunCheckpoint` / EventLog | Module runtime state |
| "Was execution authorized?" | `ActionIntent` + Policy Decision Event (`actionAuthorized`) | `ActionProposal` alone |
| "Did execution start?" | `ExecutionAttempt` (`STARTED_UNKNOWN`, `COMPLETED`, or `FAILED`) | Pre-execution `RunCheckpoint` |
| "Did execution finish?" | `ExecutionAttempt` (`COMPLETED`/`FAILED`) + `ExecutionReceipt` | `ActionIntent` |
| "Did external side effect become durable?" | `ExecutionReceipt` / `EvidenceResolution.completed` | `RunCheckpoint` or `Observation` alone |
| "Is side-effect state known after crash?" | `EvidenceResolution` (`completed`, `notStarted`, `unknown`, `unavailable`) | Absence of receipt alone |
| "Was an observation persisted?" | `Observation` record in `RunCheckpoint` / EventLog | Module output string |
| "Was StateUpdate committed?" | `AgentRuntime` `GoalStatus` | `StateJournalEntry` alone or `Evaluation` |

## 3. Lifecycle State Model

The M7 execution pipeline is modeled as a formal deterministic state machine:

```text
Run → Cycle → Action → ExecutionAttempt → Evidence Resolution → Observation → StateUpdate → Audit
```

For every state transition, preconditions, durable evidence, failure windows, and recovery decisions MUST be explicitly defined:

### 3.1 State Transitions Table

| Transition | Precondition | Durable Evidence Generated | Failure Window | Recovery Decision |
|---|---|---|---|---|
| **Run Initialized** | Valid `GoalID`, Goal in `AgentRuntime` is `.active` or `.proposed` | `RunRecord(status: .initialized)` + Event `runInitialized` | Disk write fails or EventLog throws | Halt run initialization fail-closed; Goal status remains unchanged |
| **Cycle Started** | `RunRecord` in `.initialized` or `.running` | Event `perceptionReceived` + `contextBuilt` | Context assembly or EventLog throws | Retry cycle or transition `RunRecord` to `.failed` |
| **Proposal Verified** | `Plan` generated, proposals verified | Pre-execution `RunCheckpoint` saved | Checkpoint store write fails | Abort cycle before Policy authorization; zero tool calls executed |
| **Attempt Initialized** | Proposal verified, `CapabilityLease` valid | `ExecutionAttempt(status: .NOT_STARTED)` | ExecutionAttemptStore write fails | Halt execution before side effect starts; Attempt stays `.NOT_STARTED` |
| **Attempt Started** | Policy authorized, lease step consumed | `ExecutionAttempt(status: .STARTED_UNKNOWN)` | Process crash mid-invocation | On recovery, invoke `ExecutionEvidenceResolver.resolve(...)` |
| **Attempt Resolved (Completed)** | Target module returns result OR resolver returns `.completed` | `ExecutionAttempt(status: .COMPLETED)` + `ExecutionReceipt` | Receipt write fails | On recovery, receipt check confirms side effect complete; skip re-execution |
| **Attempt Resolved (Unresolved)** | Crash recovery finds evidence `.unknown` or `.unavailable` for non-idempotent target | `ExecutionAttempt(status: .UNRESOLVED)` | Disk write fails or recovery interrupted | Transition `RunRecord.status = .interrupted`; halt fail-closed without re-execution or synthetic Observation |
| **Observation Persisted** | Attempt completed or failed with evidence | `Observation` recorded in post-execution `RunCheckpoint` | Post-execution checkpoint write fails | Recover `Observation` from `ExecutionReceipt` without re-executing action |
| **StateUpdate Prepared** | Evaluation & Reflection complete | `StateJournalEntry(status: .prepared)` with bound `EventID` persisted | Journal write fails | Abort state update; Goal status stays in previous valid state |
| **State Committed** | Journal prepared | `AgentRuntime` updates `GoalStatus` | `AgentRuntime` state update throws | Roll back journal to `.prepared` / `.aborted` |
| **Audit Committed** | State committed | Event `stateUpdated` appended to `EventLog` with bound `EventID` | EventLog throws | Re-try event append via journal recovery protocol using original `EventID` |
| **Transaction Finalized** | Audit committed | `StateJournalEntry(status: .finalized)` | Finalize write fails | Journal recovery completes finalization using original `EventID` without re-applying state |
| **Run Completed** | State update finalized | `RunRecord(status: .completed)` | RunRecord write fails | Re-assert `.completed` on run record reconciliation |

## 5. Execution Attempt & Evidence Resolution Contract

### 5.1 First-Class Identity & Lifecycle
Every tool or module execution MUST be assigned a unique `ExecutionAttemptID` and an `idempotencyKey` derived deterministically:
`idempotencyKey = SHA256(RunID + GoalID + CycleIndex + ActionID + ToolID)`

The attempt lifecycle progresses through strict stages:
1. `NOT_STARTED`: Attempt record created on disk before invocation.
2. `STARTED_UNKNOWN`: Attempt updated on disk immediately prior to module dispatch.
3. `COMPLETED`: Attempt updated on disk with `receiptRef` after target module execution returns or evidence resolution yields `.completed`.
4. `FAILED`: Attempt updated on disk after target module execution throws or times out with confirmed non-execution / failure evidence.
5. `UNRESOLVED`: Attempt marked on disk during crash recovery when execution evidence is `.unknown` or `.unavailable` for a non-idempotent action.

### 5.2 Execution Evidence Resolver Contract

Execution targets and external integration boundaries MUST expose an evidence resolution interface conforming to the following architectural contract:

```swift
public enum EvidenceResolution: Sendable, Codable, Equatable {
    case completed(ExecutionReceipt)
    case notStarted
    case unknown
    case unavailable
}

public protocol ExecutionEvidenceResolver: Sendable {
    func resolve(
        attemptID: ExecutionAttemptID,
        idempotencyKey: String
    ) async throws -> EvidenceResolution
}
```

### 5.3 Target Capability Declaration

Execution targets MUST explicitly declare their capability characteristics:

```swift
public enum ExecutionIdempotencyClass: String, Sendable, Codable, Equatable {
    case idempotent
    case nonIdempotent
}

public struct ExecutionTargetCapability: Sendable, Codable, Equatable {
    public let toolID: ToolID
    public let idempotencyClass: ExecutionIdempotencyClass
    public let supportsEvidenceResolution: Bool
}
```

### 5.4 Normative Resolution Semantics for `STARTED_UNKNOWN`

When recovering an execution run where an `ExecutionAttempt` is in `STARTED_UNKNOWN` status, `RunRecoveryEngine` MUST invoke `ExecutionEvidenceResolver.resolve(...)` and strictly apply the following semantics:

1. **`completed(receipt)`**: Authoritative evidence confirms side-effect completion.
   - `ExecutionAttempt` transitions to `.COMPLETED`.
   - `Observation` is synthesized from `receipt`.
   - Re-execution MUST NOT occur.
   - Orchestration resumes post-execution cycle evaluation.

2. **`notStarted`**: Authoritative evidence confirms side-effect did NOT begin.
   - `ExecutionAttempt` transitions to `.NOT_STARTED` (or `.failed` with non-execution status).
   - Recovery MAY re-authorize via Policy and re-execute action if lease is valid.

3. **`unknown`**: System cannot determine whether execution occurred.
   - `ExecutionAttempt` transitions to `.UNRESOLVED`.
   - `UNKNOWN` MUST NOT be converted to `FAILED` or `NOT_STARTED`.
   - No synthetic successful or failed `Observation` may be created.
   - If target capability is `.nonIdempotent`, re-execution is STRICTLY FORBIDDEN.
   - `RunRecord.status` transitions to `.interrupted` (or `.failed` with unresolved state payload). Run halts fail-closed requiring operator intervention.

4. **`unavailable`**: Evidence resolution mechanism is unreachable or timed out.
   - `UNAVAILABLE` MUST NOT be converted to `NOT_STARTED` or `FAILED`.
   - No synthetic observation may be created. Re-execution of non-idempotent side effects is STRICTLY FORBIDDEN.
   - `RunRecord.status` transitions to `.interrupted` (or `.failed` with unresolved state payload). Run halts fail-closed.

## 6. Checkpoint Contract

1. **Pre-Execution Checkpoint**: Captured after proposal verification and stored to `RunCheckpointStore` before Policy authorization or `ExecutionAttempt` initialization.
2. **Post-Execution Checkpoint**: Captured after module execution and `Observation` generation, recording updated `completedObservations` and cycle status.
3. **Snapshot Isolation**: Checkpoints represent logical orchestrator progress. Recovery MUST cross-reference `RunCheckpoint` with `ExecutionAttemptStore` and `AgentRuntime` before resuming execution.

## 7. Execution Evidence Contract

Side-effect evidence MUST be backed by a durable `ExecutionReceipt` generated by or registered with the target execution module:
- `ExecutionReceipt` MUST contain `receiptID`, `attemptID`, `toolID`, `idempotencyKey`, and `timestamp`.
- An `Observation(succeeded: true)` referencing a tool execution MUST be supported by an `ExecutionReceipt`.
- If an `ExecutionReceipt` is present on disk or returned via `EvidenceResolution.completed`, side-effect completion is authoritative even if `Observation` or post-execution `RunCheckpoint` write failed.

## 8. StateUpdate Transaction Protocol & Stable EventID

To eliminate state/audit divergence (Issue #23) without relying on infallible in-memory rollback, M7 specifies a **Durable Write-Ahead Journal Protocol with Stable Event Identity**:

### 8.1 Stable Event Identity Origin & Binding
1. **Identity Assignment**: Before `AgentRuntime.applyStateUpdate(...)` or `EventLog.append(...)` is invoked, the orchestrator generates a stable `EventID` and canonical event payload string.
2. **Journal Persistence**: The `EventID` and `canonicalEventPayload` are durably written to `StateJournalEntry` on disk in `.prepared` status.
3. **Immutability Invariant**: Once written to the journal, the `EventID` and `canonicalEventPayload` MUST NOT be changed during retries or recovery passes.

### 8.2 EventLog Idempotency Contract

The `EventLog` MUST enforce idempotent append by `EventID`:

```swift
public protocol EventLogAppending: Sendable {
    func append(eventID: EventID, payload: String) async throws
}
```

Semantics for `EventLog.append(eventID, payload)`:
- **First Call (New EventID)**: Appends event to log; returns success.
- **Retry Call (Same EventID + Identical Payload)**: Recognizes existing `EventID` with identical payload. Returns success without appending a duplicate record (**idempotent success**; exactly one durable event exists).
- **Conflicting Call (Same EventID + Conflicting Payload)**: Throws `EventLogError.conflictingPayload`. The operation fails closed as a corruption / integrity violation.

### 8.3 WAL Journal Execution Flow & Crash Recovery

```text
[StateUpdate Prepared] → Persist StateJournalEntry(.prepared, eventID, payload)
         ↓
[State Committed]    → AgentRuntime.applyStateUpdate(...) → Update Journal(.stateCommitted)
         ↓
[Audit Committed]    → EventLog.append(eventID, payload)  → Update Journal(.auditCommitted)
         ↓
[Finalized]          → Update Journal(.finalized)
```

Recovery Rules for Interrupted WAL Transactions:
- **Crash in `.prepared`**: State was NOT committed to `AgentRuntime`. Recovery marks journal `.aborted`. Goal state remains unchanged.
- **Crash in `.stateCommitted`**: State WAS committed to `AgentRuntime`, but `EventLog.append` was not finalized. Recovery reads stored `eventID` and `canonicalEventPayload` from `StateJournalEntry` and re-invokes `EventLog.append(entry.eventID, entry.canonicalEventPayload)`. Upon success, journal updates to `.finalized`. No duplicate event is emitted.
- **Crash in `.auditCommitted`**: Both state and event appends succeeded, but journal finalization disk write failed. Recovery re-applies `EventLog.append(entry.eventID, entry.canonicalEventPayload)` (which succeeds idempotently) and updates journal to `.finalized`.

## 9. Recovery Decision Matrix

The following normative matrix defines the required recovery decision for every possible combination of attempt status, evidence resolution, checkpoint state, and runtime status:

| Attempt Status | Target Idempotency Class | Evidence Resolution Outcome | Checkpoint Observation | AgentRuntime GoalStatus | Required Recovery Decision & Action | Forbidden Outcome |
|---|---|---|---|---|---|---|
| **`NOT_STARTED`** | Any | N/A | Absent | `.active` | Re-verify Policy & CapabilityLease; safe to execute. | Executing tool without Policy re-verification. |
| **`STARTED_UNKNOWN`** | Any | **`COMPLETED(receipt)`** | Present | `.active` | Do NOT re-execute tool. Resume cycle from post-execution checkpoint. | Re-executing completed tool. |
| **`STARTED_UNKNOWN`** | Any | **`COMPLETED(receipt)`** | **Absent** | `.active` | Do NOT re-execute tool. Re-hydrate `Observation` from receipt, persist checkpoint, resume evaluation. | Re-executing tool or marking goal failed. |
| **`STARTED_UNKNOWN`** | Any | **`NOT_STARTED`** | Absent | `.active` | Mark attempt `.NOT_STARTED` or `.failed`. Re-verify Policy/lease & re-execute if authorized. | Blindly executing without re-verification. |
| **`STARTED_UNKNOWN`** | **`nonIdempotent`** | **`UNKNOWN`** | Absent | `.active` | Transition attempt to `.UNRESOLVED`. Transition `RunRecord` to `.interrupted` / `.failed`. Halt fail-closed. | Blind re-execution; synthesizing fake Observation (`true` or `false`). |
| **`STARTED_UNKNOWN`** | **`nonIdempotent`** | **`UNAVAILABLE`** | Absent | `.active` | Transition attempt to `.UNRESOLVED`. Transition `RunRecord` to `.interrupted` / `.failed`. Halt fail-closed. | Treating `UNAVAILABLE` as `NOT_STARTED`; blind re-execution. |
| **`STARTED_UNKNOWN`** | **`idempotent`** | **`UNKNOWN`** / **`UNAVAILABLE`** | Absent | `.active` | Re-verify Policy & CapabilityLease. If authorized, safe to re-execute with same `idempotencyKey`. | Re-executing without Policy/lease re-verification. |
| **`COMPLETED`** | Any | Present / Verified | Present | `.active` | Do NOT re-execute tool. Resume cycle from post-execution checkpoint. | Re-executing tool. |
| **WAL `.stateCommitted`** | N/A | N/A | N/A | `.active` | Replay `EventLog.append(entry.eventID, entry.payload)` using stored `EventID`. Finalize journal. | Generating new `EventID`; creating duplicate audit events. |
| **WAL Same `EventID` + Same Payload** | N/A | N/A | N/A | Any | `EventLog` succeeds idempotently; exactly 1 event persisted. | Appending duplicate event record. |
| **WAL Same `EventID` + Conflict Payload** | N/A | N/A | N/A | Any | Fail closed with `EventLogError.conflictingPayload` / integrity violation. | Overwriting event log or ignoring payload mismatch. |
| **Any Status** | Any | Any | Any | **`.completed`** | Do NOT execute tool. Reconcile `RunRecord.status = .completed`, finalize state journal. | Executing tool on completed goal. |
| **Any Status** | Any | Any | Any | **`.aborted`** | Do NOT execute tool. Reconcile `RunRecord.status = .failed` or `.interrupted`. | Executing tool on aborted goal. |
| **Corrupt Checkpoint / Attempt** | N/A | N/A | N/A | `.active` | Fail closed. Transition `RunRecord.status = .failed`, submit `StateUpdate(.aborted)`. | Executing action from corrupt state. |

## 10. RunState ↔ GoalState Mapping

`AgentRuntime` remains the sole authority for `AgentState` and `GoalStatus`. `RunRecord.status` tracks execution run progress and MUST reconcile cleanly with `AgentRuntime`:

| `AgentRuntime` `GoalStatus` | `RunRecord.status` | Reconciliation Rules & Priority |
|---|---|---|
| `.proposed` | `.initialized` | Run registered; goal awaiting activation. |
| `.active` | `.running` / `.checkpointed` | Run executing active cognitive cycles. |
| `.completed` | `.completed` | Goal completed in `AgentRuntime`. `RunRecord` MUST be set to `.completed`. |
| `.aborted` | `.failed` / `.interrupted` | Goal aborted in `AgentRuntime`. `RunRecord` MUST be set to `.failed` or `.interrupted`. |
| `.blocked` | `.paused` | Goal paused/blocked in `AgentRuntime`. `RunRecord` MUST be set to `.paused`. |

### 10.1 Conflict Resolution Invariants
1. If `AgentRuntime` indicates `.completed` or `.aborted`, but `RunRecord` indicates `.running`, `AgentRuntime` status takes precedence. `RunRecord` MUST transition to `.completed` or `.failed` without executing side effects.
2. `RunLifecycleManager` MUST NOT mutate `AgentRuntime` goal state directly. It MUST request state updates via `AgentRuntime.applyStateUpdate(_:)`.

## 11. CapabilityLease Contract

`CapabilityLease` defines dynamic time-bounded and step-bounded execution limits:

### 11.1 Behavioral Specifications
- **Lease Owner**: Granted per `RunID` by Policy / Capability Governor.
- **Run Ownership**: A lease is strictly bound to a single `RunID`. Leases MUST NOT cross run boundaries.
- **Atomic Step Consumption**: Step consumption `consume(step)` MUST be atomic.
- **Max-Step Invariant**: `consume(step)` MUST enforce `currentStepCount + step <= maxStepCount`. If `currentStepCount + step > maxStepCount`, `consume` MUST throw `CapabilityLeaseError.maxStepsExceeded` and deny execution.
- **Expiration Check**: `isExpired` evaluates `currentTime >= expiresAt`. An expired lease MUST evaluate as invalid and deny execution.
- **Revocation**: A lease MAY be explicitly revoked. A revoked lease MUST deny all subsequent step consumptions.
- **Concurrent Consume Behavior**: Concurrent `consume` operations on the same lease MUST be serialized atomically (e.g. within actor isolation). Concurrent requests MUST NOT race to exceed `maxStepCount`.
- **Termination Behavior**: Upon run termination (`.completed`, `.failed`, `.aborted`), any active lease for that `RunID` is automatically invalidated.

## 12. Failure Semantics

M7 enforces strict fail-closed classification across all failure domains:

1. **Transient Execution Failure**: Tool timeout or network error. Recorded in `Observation(succeeded: false)`. Cycle evaluation decides whether to `.continue` or `.abort`.
2. **Permanent Execution Failure**: Unregistered tool ID or schema validation failure. Recorded in `Observation(succeeded: false)`. Evaluation returns `.abort`.
3. **Interrupted Execution**: Process crash during cycle. On boot, `RunRecoveryEngine` executes the Recovery Decision Matrix using durable `ExecutionAttempt`, `ExecutionReceipt`, and `ExecutionEvidenceResolver` evidence.
4. **Indeterminate Execution**: Execution evidence is `UNKNOWN` or `UNAVAILABLE` for a non-idempotent action. Transition to `.UNRESOLVED` attempt status and `.interrupted` run state fail-closed without re-execution or synthetic Observation.
5. **Persistence Failure**: Disk write fails for Checkpoint, ExecutionAttempt, or Journal. Execution cycle halts fail-closed before dispatching side effects.
6. **Audit/Event Failure**: `EventLog.append` throws. StateJournal protocol recovers audit consistency fail-closed using original `EventID`.
7. **Recovery Failure**: Checkpoint or attempt store is corrupt/unreadable. Recovery engine transitions `RunRecord` to `.failed` and requests goal abort.

## 13. Security / Secret Isolation

1. **Credential Isolation**: Secrets, API keys, bearer tokens, and credentials MUST NOT be stored in `RunRecord`, `RunCheckpoint`, `ExecutionAttempt`, `ExecutionReceipt`, `StateJournalEntry`, `ExecutionEvent`, or log metadata.
2. **Redaction Boundary**: Tool parameters or payloads containing authorization fields MUST be redacted prior to persisting checkpoints, receipts, or audit events.
3. **Lease Isolation**: `CapabilityLease` permissions are scoped strictly to the authorized `RunID` and cannot be hijacked by concurrent runs.

## 14. Concurrency

1. **Actor Boundaries**:
   - `AgentRuntime`: Actor owning `AgentState` and `GoalStore`.
   - `RunLifecycleOwner`: Actor owning `RunRecord` and run status progression.
   - `ExecutionBoundary`: Actor managing `ExecutionAttempt` lifecycle and receipt verification.
   - `RecoveryEngine`: Actor orchestrating crash recovery workflows.
2. **Sendable Isolation**: All contracts, artifacts, receipts, and events MUST conform to `Sendable`.
3. **Multi-Run Isolation**: Concurrent runs MUST operate on distinct `RunID`s and distinct `GoalID`s. Two concurrent runs MUST NOT mutate the same goal or lease.

## 15. Verification Matrix

The M7 specification defines explicit, observable verification test specifications covering all recovery and failure windows:

| Case ID / Feature | Initial Durable State | Failure Injected | Recovery Input | Required Durable Result | Forbidden Outcome |
|---|---|---|---|---|---|
| **1. Crash Before Execution** | Pre-execution checkpoint on disk | Process killed before `ExecutionAttempt` created | Run ID & Goal ID | Attempt `NOT_STARTED`; safe to re-verify Policy & start | Executing tool without Policy re-verification |
| **2. STARTED_UNKNOWN + Receipt Found** | `ExecutionAttempt(status: .STARTED_UNKNOWN)` | Process killed during execution | Resolver returns `completed(receipt)` | Attempt `COMPLETED`; Observation synthesized from receipt | Re-executing completed tool |
| **3. STARTED_UNKNOWN + NOT_STARTED Evidence** | `ExecutionAttempt(status: .STARTED_UNKNOWN)` | Process killed during execution | Resolver returns `notStarted` | Attempt `NOT_STARTED`; safe to re-verify & start | Blind re-execution without Policy re-verification |
| **4. STARTED_UNKNOWN + UNKNOWN Evidence** | `ExecutionAttempt(status: .STARTED_UNKNOWN)`, non-idempotent tool | Process killed during execution | Resolver returns `unknown` | Attempt `.UNRESOLVED`; `RunRecord.status = .interrupted`; halt fail-closed | Blind retry; synthesizing fake Observation (`true` or `false`) |
| **5. STARTED_UNKNOWN + UNAVAILABLE Evidence** | `ExecutionAttempt(status: .STARTED_UNKNOWN)`, non-idempotent tool | Process killed during execution | Resolver returns `unavailable` | Attempt `.UNRESOLVED`; `RunRecord.status = .interrupted`; halt fail-closed | Treating `UNAVAILABLE` as `NOT_STARTED`; blind re-execution |
| **6. Non-Idempotent + Unknown Truth** | `ExecutionAttempt(status: .STARTED_UNKNOWN)`, non-idempotent tool | Evidence resolver fails or yields indeterminate status | Recovery scan on boot | Run state `.interrupted` / `.failed`; zero re-executions | Re-executing non-idempotent side effect |
| **7. Duplicate Recovery Attempt** | `RunRecord(status: .recovering)` | Second recovery invocation triggered concurrently | Active Run ID | Second invocation waits or returns idempotent result | Duplicate state updates or tool executions |
| **8. Event Append Succeeded + Journal Finalize Failed** | `StateJournalEntry(.stateCommitted, eventID: E1)` | Disk write for journal finalize fails after `EventLog.append` | WAL recovery scan | `EventLog.append(E1)` succeeds idempotently; journal updated to `.finalized` | Generating new `EventID`; creating duplicate audit events |
| **9. Recovery Retries Same EventID** | `StateJournalEntry(.stateCommitted, eventID: E1)` | Process crash after state commit | WAL recovery scan | Re-uses exact `EventID` `E1` and payload | Re-generating a fresh `EventID` |
| **10. Same EventID + Identical Payload** | `EventLog` contains event `E1` | WAL recovery re-appends `E1` with same payload | `EventLog.append(E1, payload)` | Returns success idempotently; log count unchanged (exactly 1 event) | Appending duplicate event record |
| **11. Same EventID + Conflicting Payload** | `EventLog` contains event `E1` with payload P1 | WAL recovery re-appends `E1` with conflicting payload P2 | `EventLog.append(E1, payload2)` | Throws `EventLogError.conflictingPayload`; fails closed | Overwriting existing event or ignoring payload mismatch |
| **12. Corrupted / Missing EventID** | `StateJournalEntry(.stateCommitted)` missing `eventID` | Disk corruption on journal file | WAL recovery scan | Journal recovery fails closed; transition `RunRecord` to `.failed` | Executing state update without valid audit event |
| **13. Missing Observation (Receipt Present)** | `ExecutionReceipt` on disk; post-checkpoint write failed | Process killed after module finished, before post-checkpoint | Recovery scan | Re-hydrate `Observation` from receipt; persist checkpoint | Re-executing tool or aborting valid execution |
| **14. Expired Capability Lease** | `CapabilityLease(expiresAt < now)` | System clock advanced past `expiresAt` | Execution request | Policy denies execution; record `Observation(succeeded: false)` | Executing action on expired lease |
| **15. Concurrent Lease Consumption** | 2 concurrent tasks consume last step | `currentStepCount = maxStepCount` | Atomic `consume(1)` call | First task succeeds; second throws `maxStepsExceeded` | `currentStepCount > maxStepCount` |
| **16. Already-Completed Goal** | AgentRuntime goal `.completed`, RunRecord `.running` | Process crashed | Run reconciliation scan | Reconcile `RunRecord.status = .completed` without tool execution | Executing tool on completed goal |
| **17. Already-Aborted Goal** | AgentRuntime goal `.aborted`, RunRecord `.running` | Process crashed | Run reconciliation scan | Reconcile `RunRecord.status = .failed` without tool execution | Executing tool on aborted goal |

## 16. M7.1 Implementation Boundary

M7.0 freezes behavioral contracts, invariants, recovery matrices, state protocols, and evidence resolution contracts. The following implementation decisions remain unfrozen for M7.1+:
- Concrete file formats for `RunStore`, `ExecutionAttemptStore`, and `StateJournalStore` (e.g. JSON, SQLite, or atomic sidecar files).
- Internal class/actor layout of orchestrators and recovery engines, provided they satisfy all protocol boundaries and ownership rules.
- Concrete network adapters for target system evidence resolvers.
- Concrete timer implementation for lease expiration checks.

---

## 17. M8+ Boundary

M8+ may introduce multi-agent network protocols, real-time audio streaming, background system daemons, or remote synchronization protocol extensions, but MUST NOT alter M7 durable execution attempts, checkpointing, StateUpdate transaction protocols, or recovery semantics.
