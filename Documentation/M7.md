# M7 Architecture Contract — Durable Run Lifecycle, Checkpointing, Interruption Recovery & Capability Bounding

Status: M7 Architectural Gate Specification (Normative; M7.0 only)

Milestone baseline: M6 baseline (merged M6 composition and semantics baseline).

This document defines the responsibilities, boundaries, ownership, control flow, evidence model, failure/recovery semantics, concurrency model, and dependency architecture required for M7 implementation. It establishes the architectural contract for durable agent execution runs, execution checkpoints, capability leasing, and interruption recovery.

Normative terms MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL have their RFC 2119 meaning.

## 2. Purpose and Scope

M6 established the integrated cognitive cycle (Perception → Context → Reasoning → Planning → ActionProposal → Verification → Policy → Execution → Observation → Evaluation → Reflection → StateUpdate). However, M6 orchestration operates imperatively in-memory within single goal execution cycles.

M7 extends the system with:
1. **Durable Run & Session Lifecycle**: Bounding goal execution within explicit, persistent execution runs (`RunID`, `RunRecord`, `RunState`).
2. **Structured Execution Checkpointing**: Persisting transactional execution state (`RunCheckpoint`) before and after execution stages.
3. **Interruption Recovery Engine**: Safely re-hydrating or resuming interrupted or crashed execution runs fail-closed based on verifiable checkpoint evidence.
4. **Capability Leasing**: Applying time-bound and step-bound capability leases before policy authorization to enforce execution budget boundaries.
5. **Correlated Provenance & Extended Audit**: Correlating `RunID`, `SessionID`, `TraceID`, `GoalID`, and `ActionID` across execution events.

M7 MUST preserve all valid M0–M6 invariants.

### 2.1 Non-goals

M7 MUST NOT define or introduce:
- Production M7 runtime implementation code in M7.0.
- A second authority for `AgentState` or goal lifecycle (`AgentRuntime` remains the sole authority).
- Bypassing Policy or `ApprovalGate`.
- Direct UI bindings or SwiftUI view-model dependencies in Kernel.
- Autonomous multi-tenant cloud orchestration daemons or vendor SDKs in Kernel.
- Swallowing errors or performing unverified implicit recovery.
- Credential material in run records, checkpoints, cognitive artifacts, events, or logs.

## 3. M0–M6 Forensic Baseline

The codebase baseline was audited across contracts, runtimes, composition, storage, memory, and tests:

1. **Layer Hierarchy**:
   `App` → `Composition` → `Kernel` → `Cognition` / `Agency` / `Policy` → `Modules` / `Skills` / `Tools` / `Providers` → `Memory` / `Storage` → `Events` / `Observability` / `Security` → `Foundation`.
2. **State Authority**:
   `AgentRuntime` is the single actor holding authoritative `AgentState` (`identity`, `lifecycle`, `phase`, `activeGoalID`) and `goalStore` (`GoalID: Goal`).
3. **Cognitive Orchestration**:
   `M6Orchestrator` coordinates the canonical M6 cycle. It requests state mutations via `StateUpdate`, which `AgentRuntime.applyStateUpdate(_:)` validates and commits.
4. **Audit and Events**:
   `ExecutionEvent` records lifecycle and cycle transitions fail-closed into `EventLog`. If `EventLog.append(_:)` throws, state updates and execution cycles abort fail-closed.
5. **Memory and Storage**:
   `PAMemory` (`FileBackedMemoryStore`) handles local memory records; `PAStorage` (`PASyncEngine`, `PASyncQueue`) handles storage sync.
6. **Existing Technical Debt**:
   - **Issue #23 (StateUpdate and Audit Consistency)**: `StateUpdate` requires supporting evidence and fail-closed audit event emission.
   - **Lack of Durable Run Execution State**: Currently, if process terminates during `M6Orchestrator.run(goalID:)`, in-flight cycle state is lost. There is no `RunRecord` or `RunCheckpoint` to inspect or recover from.

## 4. M7 Problem Definition

After M6, goal execution can progress through planning, policy authorization, and execution, but execution progress is transient. If an agent process is suspended, interrupted, or crashes mid-cycle:
1. Active execution state disappears without a durable trace of where execution stopped.
2. The system cannot distinguish between an unstarted goal, an in-progress goal interrupted mid-tool execution, and a completed goal whose state update failed to persist.
3. Execution capabilities are granted statically without dynamic budget, time, or step boundaries (leases).

M7 solves this by introducing a **Durable Run Execution Boundary**:
- Bounding execution into a `RunRecord` identified by a `RunID`.
- Capturing `RunCheckpoint` snapshots at deterministic cycle boundaries.
- Providing a `RunRecoveryEngine` that inspects `RunCheckpoint` and `AgentRuntime` goal state to recover or fail closed cleanly.
- Enforcing `CapabilityLease` constraints during Policy authorization.

---

## 5. Goals

1. **Single Source of State Truth**: Maintain `AgentRuntime` as the sole authority for `AgentState` and goal status.
2. **Durable Execution Tracking**: Persist execution run progress (`RunRecord`, `RunCheckpoint`) without creating conflicting state logic.
3. **Deterministic Interruption Recovery**: Enable fail-closed recovery of interrupted runs using verified checkpoint evidence.
4. **Capability Bounding**: Restrict action execution through explicit, time-bounded and step-bounded `CapabilityLease`s.
5. **Audit Trace Correlation**: Correlate all execution events with `RunID` alongside `TraceID` and `GoalID`.

## 6. M6 Preservation Invariants

The canonical M6 flow remains authoritative:

```text
Perception
  → Context
  → Reasoning
  → Planning
  → ActionProposal
  → Verification
  → Policy Authorization
  → Execution
  → Observation
  → Evaluation
  → Reflection
  → StateUpdate
  → Continue / Complete / Abort
```

Specific M6 invariants that remain immutable:
1. **Executor Success ≠ Verified Success**: Module execution returning success does not equal verification or evaluation success.
2. **Reflection is Post-Execution**: Reflection occurs after `Observation` and `Evaluation`.
3. **Fail-Closed Audit**: State updates and runtime transitions MUST fail closed if event logging fails.
4. **Policy Enforcement**: No proposal MAY execute without Policy authorization (and optional `ApprovalGate`).
5. **Single Active Goal per Runtime**: An `AgentRuntime` instance MUST NOT execute multiple active goals simultaneously.

## 7. M7 Ownership Model

Every M7 artifact MUST have exactly one authoritative producer and owner:

| Artifact | Producer / Authority | Consumers | Durable? | Authority Scope |
|---|---|---|---|---|
| `RunID` | Run Boundary / Orchestrator | Events, Checkpoints, Audit, Recovery | Yes (Value) | Execution run identity |
| `RunRecord` | `RunLifecycleManager` | `AgentRuntime`, `RunRecoveryEngine`, Audit | Yes (Store backed) | Execution run metadata & state |
| `RunCheckpoint` | Orchestrator Checkpoint Stage | `RunRecoveryEngine`, Orchestrator | Yes (Store backed) | Transactional cycle snapshot |
| `CapabilityLease` | Capability Governor / Policy | Agency Execution | Transient (Memory) | Bounded execution permission |
| `RecoveryResult` | `RunRecoveryEngine` | Orchestrator, `AgentRuntime` | Transient | Interruption recovery evaluation |
| `StateUpdate` | Cognition / Agency | `AgentRuntime` (validates & commits) | Yes (via AgentRuntime) | State mutation request |
| `ExecutionEvent` | Kernel / Orchestrator | `EventLog` | Yes (EventLog) | Immutable audit evidence |
| `AgentState` / `Goal` | `AgentRuntime` | Whole System | **Authoritative State** | **Sole system state authority** |

### 7.1 Non-Duplication Principle
`RunRecord` and `RunCheckpoint` MUST NOT become a second authority for `AgentState` or `Goal` status. `RunRecord.status` tracks the execution run lifecycle (`initialized`, `running`, `checkpointed`, `paused`, `recovering`, `completed`, `failed`, `interrupted`), whereas `AgentRuntime.goalStore` remains the sole authority for `GoalStatus`.

## 9. M7 Control Flow

### 9.1 Normal Run Execution Flow

```text
Run Initialization (RunRecord created)
      ↓
AgentRuntime Goal Activation
      ↓
Cognitive Cycle Start (Perception → Context → Reasoning → Planning → Proposals → Verification)
      ↓
Pre-Execution Checkpoint (RunCheckpoint stored)
      ↓
Capability Lease Check & Policy Authorization
      ↓
Execution (Action Proposals → Observations)
      ↓
Post-Execution Checkpoint (RunCheckpoint updated)
      ↓
Evaluation & Reflection
      ↓
Authoritative StateUpdate (AgentRuntime)
      ↓
Run Record Status Update (completed / paused / continue next cycle)
```

### 9.2 Normative Sequence Steps

1. **Run Registration**:
   - `RunLifecycleManager` generates `RunID` and creates `RunRecord` with status `.initialized`.
   - Event `runInitialized` is emitted with `runID`, `sessionID`, `goalID`, `traceID`.
2. **Goal Activation**:
   - `AgentRuntime.activate(goalID:)` is invoked. If goal status transition fails, `RunRecord.status` transitions to `.failed` and run halts.
3. **Cognitive Cycle & Checkpointing**:
   - Perception, Context, Reasoning, Planning, Proposals, and Verification execute.
   - If Verification succeeds, a `RunCheckpoint` is created containing `pendingProposals`, `cycleIndex`, and `traceID`, and saved to `RunCheckpointStore`.
   - Event `runCheckpointed` is emitted.
4. **Capability Leasing & Authorization**:
   - Policy evaluates `ActionIntent` against `CapabilityLease`.
   - If lease is expired or step count exceeded, event `capabilityLeaseExpired` is emitted, policy denies execution, and observation records lease rejection.
5. **Execution & Evaluation**:
   - Proposals execute through `ModuleRuntime`. Observations are recorded.
   - Post-execution `RunCheckpoint` is persisted.
   - Evaluation and Reflection are produced.
6. **State Update & Completion**:
   - `StateUpdate` is submitted to `AgentRuntime.applyStateUpdate(_:)`.
   - Upon successful state update and event logging, `RunRecord.status` transitions to `.completed` (or `.running` if disposition is `.continue`).

## 10. Interruption Recovery Flow

If the process crashes or is killed during execution, `RunRecord` remains in `.running` or `.checkpointed` status on disk.

```text
Process Boot / Recovery Trigger
      ↓
RunRecoveryEngine scans RunStore for unclosed runs
      ↓
Inspect latest RunCheckpoint from RunCheckpointStore
      ↓
Cross-check GoalStatus in AgentRuntime
      ↓
Validate Checkpoint Integrity & Evidence
      ↓
  ┌───────────────────────────┬───────────────────────────┐
  │ Checkpoint Valid          │ Checkpoint Corrupt/Missing│
  ▼                           ▼                           ▼
Resume from Checkpoint      Restart Cycle               Mark Run Failed
(re-run pending proposals)  (re-enter Perception)       (Set Goal Aborted)
```

### 10.1 Recovery Invariants
- **No Unverified Execution**: If a checkpoint indicates an action was authorized but no `Observation` exists, the recovery engine MUST re-verify Policy authorization before re-executing.
- **Goal Status Alignment**: If `AgentRuntime` records the goal as `.completed` or `.aborted`, but `RunRecord` is `.running`, `RunRecord` MUST be updated to match `AgentRuntime` without re-executing actions. `AgentRuntime` state is always authoritative.

## 11. Failure Semantics

M7 specifies fail-closed failure classification:

| Failure Type | Description | System Behavior |
|---|---|---|
| **Transient Execution Failure** | Module or tool timeout / network error | Recorded in `Observation(succeeded: false)`. Evaluation determines `.continue` or `.abort`. |
| **Permanent Execution Failure** | Unregistered tool ID / fatal schema error | Recorded in `Observation`. Evaluation returns `.abort`. `StateUpdate` sets goal `.aborted`. |
| **Interrupted Execution** | Process crash / kill during cycle | On restart, `RunRecoveryEngine` recovers via latest valid `RunCheckpoint`. |
| **Persistence Failure** | Checkpoint or RunStore write fails | Execution cycle halts fail-closed. Action MUST NOT execute if pre-execution checkpoint fails to store. |
| **Audit/Event Failure** | `EventLog.append` throws | Operation aborts. State changes rolled back. Goal status remains in previous valid state. |
| **Recovery Failure** | Checkpoint corrupted or missing | Recovery engine transitions `RunRecord` to `.failed` and requests goal abort. |
| **Lease Expiration** | Capability lease step/time limit exceeded | Policy evaluation returns `.deny`. Proposal fails execution. |

## 12. State Authority & Issue #23 Resolution

M7 enforces strict state isolation across six distinct domains:

```text
Authoritative AgentState (AgentRuntime)
      ≠
Audit / Event Evidence (EventLog)
      ≠
Memory State (MemoryStore)
      ≠
Storage Sync State (PAStorage)
      ≠
Run & Checkpoint State (RunStore / CheckpointStore)
      ≠
Transient Execution State (Orchestrator Stack)
```

### 12.1 Resolution of Issue #23 (StateUpdate Audit Consistency)
Issue #23 identified the risk of `StateUpdate` committing state without verifiable audit trail consistency.
Under M7:
1. `StateUpdate` MUST include non-empty evidence referencing `disposition`, `reason`, `reflection`, `observationIDs`, and `runID`.
2. `AgentRuntime.applyStateUpdate(_:)` MUST commit state update and emit `.stateUpdated` event within an atomic transaction boundary.
3. If `.stateUpdated` event emission fails, the goal state mutation MUST be rolled back in `AgentRuntime`, and `RunRecord` MUST NOT transition to `.completed`.

## 14. Persistence Contracts

M7 introduces storage contracts for run tracking:

```swift
public protocol RunStoring: Sendable {
    func saveRun(_ record: RunRecord) async throws
    func fetchRun(id: RunID) async throws -> RunRecord?
    func fetchUnclosedRuns() async throws -> [RunRecord]
}

public protocol RunCheckpointStoring: Sendable {
    func saveCheckpoint(_ checkpoint: RunCheckpoint) async throws
    func fetchLatestCheckpoint(runID: RunID) async throws -> RunCheckpoint?
    func fetchCheckpoints(runID: RunID) async throws -> [RunCheckpoint]
}
```

Stores MUST execute atomic file/database writes and fail closed on corrupt snapshots.

## 15. Concurrency Model

1. **Actor Boundaries**:
   - `AgentRuntime`: Single actor owning `AgentState` and `GoalStore`.
   - `RunLifecycleManager`: Actor owning `RunRecord` state updates.
   - `M7Orchestrator`: Actor coordinating individual goal execution cycles.
   - `RunRecoveryEngine`: Actor executing recovery workflows.
2. **Sendable Isolation**: All cross-actor contracts, artifacts, and event payloads MUST conform to `Sendable`.
3. **Multi-Run Isolation**: Concurrent execution runs MUST operate on distinct `RunID`s and distinct `GoalID`s. Two concurrent runs MUST NOT mutate the same goal.

---

## 16. Security & Credential Boundary

1. **Credential Isolation**: Secrets, API keys, tokens, and authorization headers MUST NOT be stored in `RunRecord`, `RunCheckpoint`, `StateUpdate`, `ExecutionEvent`, or log output.
2. **Redaction Boundary**: Parameters containing sensitive keys MUST be redacted before persisting checkpoints or emitting events.
3. **Capability Lease Isolation**: `CapabilityLease` grants permissions strictly within the requesting `RunID` and expires automatically upon run termination or timeout.

Dependency direction remains downward only:

```text

  ↓

  ↓
Kernel (AgentRuntime, M7Orchestrator, RunLifecycleManager, RunRecoveryEngine)
  ↓
Cognition / Agency / Policy
  ↓
Modules / Skills / Tools / Providers
  ↓
Memory / Storage (RunStore, CheckpointStore, MemoryStore, PAStorage)
  ↓
Events / Observability / Security
  ↓
```

### Prohibited Patterns
- NO service locators or global singletons.
- NO Kernel dependencies on concrete provider targets (`PAProvidersGrok`, `PAProvidersOpenAI`, etc.).
- NO Kernel dependencies on SwiftUI or UIKit.
- NO direct mutation of `AgentRuntime` state from `RunLifecycleManager` or `RunRecoveryEngine` without calling `applyStateUpdate` or goal management protocol methods.

## 19. Verification Gate (Test Specifications)

Before M7.1 runtime code is accepted, the implementation MUST pass the following test specifications:

| Invariant / Feature | Failure Scenario | Expected Behavior | Observable Evidence |
|---|---|---|---|
| **Durable Run Registration** | `RunRecord` creation fails | Execution halts before goal activation | Error thrown; no goal state change |
| **Pre-Execution Checkpoint** | Checkpoint store fails write | Action proposals DO NOT execute | `runCheckpointed` event absent; actionExecuted absent; error thrown |
| **Capability Lease Expiration** | Lease expires mid-run | Policy denies action execution | `capabilityLeaseExpired` event emitted; actionDenied event logged |
| **Interruption Recovery** | Process terminated during cycle | Recovery engine re-hydrates run from checkpoint | `runRecovered` event emitted; pending proposals re-verified |
| **Goal Authority Precedence** | AgentRuntime goal status `.aborted`, RunRecord status `.running` | Recovery engine aligns RunRecord to `.aborted` without executing | RunRecord status updated to `.failed`/`.interrupted`; zero tool executions |
| **Fail-closed Audit Rollback** | EventLog throws during StateUpdate | Goal status change rolled back | Goal status remains unchanged in `AgentRuntime` |
| **Secret Isolation** | Proposal contains API token | Checkpoint and events redact token | Token string absent in `RunCheckpoint` and `ExecutionEvent.payload` |
